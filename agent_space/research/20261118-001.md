## 1. 결론

가장 먼저 줄일 비용은 **작은 UI 정보 조회가 전체 CSV·자산 복사와 행 순회를 유발하는 구조**다. 이어서 전체 revision 구독에 의한 반복 조회와 명령 내부의 전체 프로젝트 복사·검증·결과 비교를 개선한다.

이 우선순위는 정적 처리량과 영향을 받는 조작 범위에 근거한다. 실제 시간 비중은 계측 후 조정한다. 프로젝트 가져오기 lifecycle 9.720초와 사용자 지연 보고는 심각성을 뒷받침하지만, 함수별 병목 순위나 개선 배수를 입증하지는 않는다.

### 2.3 처리량을 비교할 기준

현재 구조의 비용은 데이터 크기와 호출 횟수를 함께 봐야 한다. 한 조작에서 조회 i의 실행 횟수를 qᵢ, 복사하는 데이터량을 Bᵢ, 검사하는 CSV 행 수를 Rᵢ라고 두면, 반복 읽기의 작업량은 대략 `Σ qᵢ × (복사 Bᵢ + 행 검사 Rᵢ)`로 추적할 수 있다. 이 식은 시간 측정값을 대신하지 않는다.

P1은 Bᵢ·Rᵢ를, P2는 qᵢ를 줄이는 개선이다. P3은 같은 참조 그래프의 중복 방문을 줄인다. P4–P5는 명령 한 번에 수행되는 전체 프로젝트 순회 횟수를 줄인다. 각 단계에서 별도 결과를 확인하면 단순히 React 호출 수만 줄고 큰 데이터 조회가 남는 상황을 구분할 수 있다.

VFS의 공유 자식이 freeze에서 다시 방문되는 횟수는 자산 수·디렉터리 깊이·루트 배열에 노출된 경로에 따라 달라진다. 현재 트리 깊이와 방문 횟수를 계측해 판단한다. 이 현상을 데이터 복사본 수 증가나 지수 시간으로 단정하지 않는다.

## 3. 정책과 보존 조건

`agent_space/policies/development-policy.md` §2.1–2.6과 `agent_space/AGENT.md`의 현재 규칙을 적용한다.

1. ProjectObject와 Frontend FSM의 현재 소유권을 유지한다. UI 입력은 기존 command·검증·참조 보정 경로를 통과한다.
2. mutation에 다시 들어가는 편집 복사본을 다른 소비자의 공용 조회 원천으로 배포하지 않는다. commit 시 대상·현재 값을 공식 경로에서 다시 확인한다.
3. 이 프로젝트의 AGENT는 임시 snapshot·cache·selector 값의 작업 범위를 제한한다. 외부 React 문서의 캐시 예시만으로 전역 Project mirror나 별도 갱신 registry를 도입할 수 없다.
4. 후보 실패 시 기존 Project를 보존하고, 현재 원본 재검사와 한 번의 commit을 유지한다. 최적화를 이유로 전역 참조·소유·geometry 불변식을 생략하지 않는다.
5. 자동 작업공간 갱신은 현재 선택 슬롯으로 제한하고, 전체 내용 갱신은 렌더링 버튼에서만 수행한다. 단순 크기·이동 변화는 기존 표시의 CSS 변환을 유지한다.
6. source-first 변경은 Source Script → pseudocode → source code 순서로 전파한다. 저장 파일 형식·ID·취소·오류·선택 의미를 보존한다.

## 4. 우선순위별 최적화안

### P0. 단계별 비용을 먼저 계측

한 조작에 대해 입력 callback → FSM/Backend command → 후보 계산·정규화·검증 → commit → 실제 결과 작성 → listener → React commit → 선택 슬롯 Plotly 완료를 구분한다. `performance.now()`와 짧은 mark/measure로 같은 조작의 구간을 연결한다. React render 중 발생한 공식 조회도 호출 수·결과 크기로 따로 기록한다.

- 측정 자료: query별 호출 수, 반환 행·bytes 포함 여부, clone/freeze/열 순회 방문 수, 후보 검증·initialize 검증 횟수, actualChanged 비교량, 할당·GC, 선택/비선택 슬롯 Plotly 호출 수.
- 사용자 응답시간은 입력부터 의미 있는 화면 갱신까지 측정한다. rAF 표식과 실제 paint 분석의 범위를 구분한다. 동기 callback 종료를 표시 완료로 간주하지 않는다.
- Firefox Profiler를 우선 사용하고 React Profiler는 배포 runtime 지원이 확인될 때 보조로 사용한다. profiling 자체 비용을 별도 기록한다.
- 진단 로그는 본문 데이터 대신 종류·크기·시간을 기록한다. 디버그 ON, 짧은 독립 workflow, 건별 저장 후 비우기를 유지한다.

### P1. 공식 조회가 필요한 값만 만들도록 축소

가장 먼저 다음 소비자별 입력·출력 계약을 Source Script에서 확정한다. 기존 전체 조회가 필요한 자산 편집·내보내기 경로는 유지한다.

| 소비자 | 필요한 공식 값 | 줄일 계산 |
| --- | --- | --- |
| 자산 트리·CSV 선택 목록 | kind/id/path/name/부모·표시 순서 | CSV rows·bytes·image bytes의 복사 |
| 휴지통 상태·표시 | 휴지통 subtree의 표시 값과 참조 개수 | 전체 프로젝트 VFS 구성 후 subtree 선택 |
| 트리 참조 badge | 대상 식별자와 공식 참조 개수 | 전체 자산 payload 반환 |
| 숫자 입력 대상 확인 | slot/chart/object/CSV 식별자, ready 상태 | 전체 chart·CSV 본문 복사와 열 정의 생성 |
| 숫자 현재 값 | 현재 대상의 해당 scalar와 필요한 companion 값 | 전체 그래프·CSV 조회 |

좁은 조회도 Backend의 동일한 현재 Project에서 계산한다. UI에 별도 자산 목록을 보관해 동기화하는 구조는 도입하지 않는다. 같은 command 내부의 함수 간 후보 전달과 다른 UI 소비자의 공용 참조는 구분한다.

**완료 근거:** 디렉터리 선택과 객체의 숫자 값 표시에서 CSV 행·bytes 복사가 발생하지 않아야 한다. 반환 형상·참조 개수·순서와 원래 기능은 동일하게 확인한다. 미리보기처럼 행이 필요한 기능의 조회는 별도로 인정한다.

### P2. 관련 값만 구독하고 순수한 표시 계산을 안정화

`useUiCommand`가 모든 control에 전체 revision과 큰 graph 조회를 요구하는 관계를 분리한다. ready·선택 식별자·현재 scalar를 현재 owner에서 저렴하게 읽고 관련 값 변화에만 화면을 갱신하도록 검토한다. 조합 snapshot은 불변·동일성 조건을 충족해야 하며, 매 getSnapshot 호출마다 새 객체를 반환하면 안 된다.

입력 중 lexical text는 해당 control이 소유한다. 대상 변경·unmount·command 시작/종료는 기존 취소·중복 실행·오류 정리 규칙을 유지한다. React 재렌더 횟수 감소를 위해 오래된 target이나 API 결과를 mutation 입력으로 재사용하지 않는다.

theme 생성은 실제 appearance 의존성에 연결한다. 접힌 영역은 현재 구현의 children 유지에 따른 조회량을 먼저 줄인다. unmount 방식은 편집값·접기·focus 보존 의미가 달라질 수 있으므로 별도 승인·설계 후 비교한다. `memo`/`useMemo`만 추가해 전체 데이터 조회를 숨기는 방안은 후순위로 둔다.

### P3. 한 번의 불변 읽기 결과를 만드는 내부 비용 축소

- `immutableProjectCopy`의 재귀 동결에 호출-local WeakSet을 사용해 같은 객체를 한 번 방문하도록 검토한다. 공유 참조 보존·순환·typed data 처리와 현재 반환 의미를 확인한다.
- 먼저 P1로 트리 payload를 축소한다. 이어 VFS 노드 구성에서 이미 분리한 payload를 다시 전체 clone하는 경계를 검토한다.
- 안전 조건은 반환 결과와 authoritative Project의 가변 객체가 공유되지 않는 것이다. 단순히 freeze나 clone을 제거하면 이 조건을 잃을 수 있다.
- typed array·bytes·Slot prototype·extra fields·직렬화 경계는 각각 확인한다. 전역 visited cache는 사용하지 않는다.

### P4. 후보 검증과 commit의 중복 비용 정리

현재 후보 helper와 initialize의 복사·정규화·전체 검증을 한 명령의 소유 흐름으로 추적한다. 일반 initialize의 안전성을 유지하면서, 동일 후보에 이미 수행한 검증을 commit 경계에서 어떻게 한 번만 수행할지 Source Script에서 확정한다.

검증된 후보는 해당 command 안에서만 소비하고 외부 변경 가능성을 차단한다. 외부 호출자가 임의의 검증 완료 flag를 넣는 경로는 허용하지 않는다. commit 직전 현재 원본 확인을 유지하며, 검증 중 후보가 바뀌면 검증 결과를 재사용하지 않는다.

첫 개선 단계에서는 전체 불변식 검증을 유지하고 중복 복사·중복 전체 검증만 제거한다. 부분 검증은 명령별 영향 범위와 전역 제약의 충족 근거가 갖춰진 뒤 별도 검토한다.

### P5. 실제 변경 결과 비교와 행 순회 축소

전체 PRE/POST 컬렉션 JSON 비교를 command-local 실제 변경 경로와 전후 데이터의 대조로 대체할 수 있는지 검토한다. 명령 의도만으로 변경 사실을 선언하면 안 된다. 삭제·간접 참조 제거·순번 이동·asset 경로 변경·no-op을 현재 결과 계약과 대조한다. 실패 시 거짓 변경 결과가 생성되지 않아야 한다.

동일 검증·열 계산 호출 안의 같은 CSV에 대해서는 한 번 계산한 결과를 그 호출의 내부 계산에만 사용하도록 검토한다. 다른 editor의 일반 읽기나 다음 command에 넘기는 장기 캐시로 확장하지 않는다.

후보의 변경된 branch만 복사하는 구조적 공유는 후순위다. 현재 정규화·검증이 객체를 수정하는지 먼저 확인하고, authoritative 원본의 재사용 branch가 수정될 수 없도록 소유권·불변성 보장이 마련된 뒤 비교한다.

## 6. 후속 실행 단위와 확인 방법

1. **계측·기준선:** 원본 사용자 프로젝트 또는 승인된 동등 fixture의 행·열·bytes·chart 수를 기록하고, 작은 프로젝트와 비교한다. 파일·프로파일·로그는 `.work`에 둔다. 배포물은 프로젝트의 정상 `dist` 빌드를 사용한다.
2. **조회 계약·소비자 수정:** P1을 한 소유권 단위로 Source Script → pseudocode → source code에 반영하고, P2의 현재 target/scalar 구독까지 대조한다.
3. **복사·동결 개선:** P3 전후의 방문 수·할당량·응답시간과 반환 격리성을 확인한다.
4. **명령 경로 개선:** P4–P5를 실제 후보/검증/commit/결과의 동일성 근거와 함께 반영한다.
5. **비교 검증:** import, 디렉터리 선택, 슬롯 선택/해제, 객체 선택, 축 설정 한 값 변경, lexical 입력, 전체 렌더링 버튼을 각각 짧게 측정한다. 같은 fixture에서 기준선과 개선본을 반복 비교하고 중앙값·최댓값·표본 수를 기록한다. 표본이 충분할 때 p95를 추가한다.

### 정합성과 완료 기준

- 선택 전용 조작은 Project 변경 command와 Plotly 전체 갱신을 만들지 않는다. 현재 선택·독립 CSV 선택의 UX 기대는 별도로 확인한다.
- 비선택 슬롯은 기존 표시를 유지한다. 전체 내용 갱신은 명시 버튼에서만 실행한다. 단순 resize/이동은 CSS 변환만 수행한다.
- 숫자 입력은 입력 중 문자열 보존, Enter/blur 한 번 확정, Escape 취소, IME, 대상 변경, async 실패 정리를 유지한다.
- 실패·취소·stale 대상·유효한 slotId 0·공유 CSV·참조 삭제·객체 순번 이동·패키지 roundtrip에서 기존 규칙을 보존한다.
- 개선 전후의 query·clone·행 순회·검증·React·Plotly 호출 수와 총 응답시간을 함께 제시한다. 아직 수치 기준선을 확보하지 못했으므로 배수·절대 시간 목표의 달성을 선언하지 않는다.
