## 선택 이유와 기각 대안

기존 public 선택은 appFSM.send 뒤 무조건 updateGraphView/resize를 수행했고 명세의 optional persistent intent orchestration이 없었다. drop 준비도 selection/render를 따로 구성했다. 이를 같은 명세 절차에 연결해야 화면 경계의 실제 호출자가 완성되므로 Adapter 추출과 caller cutover를 한 패치로 수행했다.

- UI/FSM에 pending type 상태를 저장하거나 domain candidate를 만드는 방향은 기각했다. current authority와 Project EFSM이 책임을 갖는다. explicit type/slot ID만 command로 전달한다.
- 선택 후 renderer가 domain을 재조회하거나 wrapper가 두 번째 renderer read를 하는 방향은 기각했다. 반환된 최종 state/projection을 한 작업 안에서 소비한다. 이를 전역 snapshot/cache나 일반 freshness 체계로 확장하지 않는다.
- reject도 기존처럼 repaint하고 resize하는 방향은 기각했다. 상위 절차의 rejected no-projection 경계와 다르다.
- 기존 continuous drop receiver를 새 framework/service로 바꾸는 방향은 기각했다. choosePlan은 useCallback([])라 collision state update에도 listener 수명이 유지된다. callback 교체가 실제 발생한다는 증거 없이 구조를 늘리지 않는다.
- 준비 오류를 finally 밖에 두는 방향은 기각했다. Source DASHBOARD_DROP_FLOW의 finally drag cleanup은 query/selection/render 준비 실패에서도 필요하다. PlusCal의 정상 준비→import→finalize 경로를 새 오류 의미로 바꾸지 않고 Source의 cleanup 의도를 실제 언어 예외 처리에 적용한다.
- 실제 native integration 대신 mock choreography를 새 suite로 늘리거나, stage3 VFS를 더 확장하는 방향은 기각했다. 현재 화면 경로와 기존 case의 필요한 assertion만 수정했다.
