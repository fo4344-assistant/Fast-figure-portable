# 20261106-007

## 목적 및 실제 기록

사용자가 누적 작업의 GitHub commit과 테스트를 명시적으로 허용했다. 로컬 app/test/build/checker 실행은 하지 않고 GitHub Actions의 최종 SHA 실행으로 검증한다.

이 패치는 실제 원격 main의 시작 `28e6dc762c75c8a2ffbbe53ed08b323f0b2b82bd`부터 의미 변경 끝 `bda8da60f958c738006782f970ff074a9affc530`까지 Git fetch 후 실제 Git 객체에서 추출한 누적 diff다. 원격에 반영된 30개 파일을 포함한다. r129–133의 구현/metadata/기존 case 변경, plan023/024, 원래 미반영 regression cleanup/실패 로그/review, 각 incremental patch001–006 및 설명을 보존한다. 정책·Source Script·PlusCal·verification·dist를 직접 변경하지 않는다. source-code133/stale과 상위 lineage는 그대로다.

## 반영 방식과 선택 이유

정책에 따라 파일별 GitHub Contents API PUT을 순차 사용했다. 매 파일마다 직전 main HEAD와 blob SHA(새 경로는 404)를 확인하고, HEAD를 재확인한 뒤 write하며 반환된 commit을 다음 write의 expected HEAD로 사용했다. 초기 원격과 로컬 HEAD는 같았으며 기존 파일은 시작 commit blob과 대조했다. 기록 순번의 대상 경로가 이미 있으면 중단하는 방식이다. 각 업로드 내용은 canonical LF이며 작업 파일의 raw CRLF를 재작성하지 않았다.

물리적으로 30개의 파일별 commit이며 하나의 atomic commit이라고 주장하지 않는다. 일관성이 필요한 파일이 일시적으로 나뉘는 Contents API 제약을 숨기지 않는다. 중간 상태의 무의미한 CI 실행을 막기 위해 이 upload commit들의 message에 [skip ci]를 사용하고, record pair까지 반영한 뒤 실제 workflow_dispatch로 최종 SHA를 검증한다. CI를 생략해 통과로 간주하는 용도가 아니다.

기존 publish-ff.cjs는 과거 Plan016 message와 저장소 밖 임시 경로를 고정하므로 그대로 재사용하지 않았다. 정책상 기본이 아닌 low-level Git Data API나 git push atomic commit으로 우회하지 않았다. 실행만을 위한 무관한 파일 변경이나 empty semantic commit도 하지 않았다. Git fetch는 실제 원격 diff 추출용이며 로컬 테스트 실행이 아니다.

## 누적 diff와 한계

원격 의미 변경 후 실제 diff를 얻어야 하므로 이 record pair 자체는 위 의미 변경 commit과 동일한 commit에 있을 수 없다. pair는 이어지는 Contents API 파일별 commit으로 기록한다. 누적 patch 자체/동명 설명은 자기 재귀 포함하지 않는다. 각 이전 incremental patch는 원래 작업 직전 WIP 기준이며 이 누적 patch가 배포된 전체 변경/rollback 추적의 기준이다.

Actions 대상은 현재 정의된 fast-figure-regression.yml(문법/4개 module·packaging 검사/inline·split 브라우저), development-layer-version.yml(base_sha=시작 SHA), pseudocode-fidelity.yml(동일 base_sha), build-distribution.yml이다. 사용자가 요청하지 않은 optional TLC나 vendor workflow는 실행하지 않는다. build workflow는 생성 dist를 별도 bot commit으로 main에 추가할 수 있으며 이를 구현 SHA와 구별해 보고한다. 실행 여부·run ID·정확한 기준 SHA·로그·결과는 실행 후 별도 근거로 확인한다. 이 설명 작성 시점에는 아직 dispatch 전이므로 pass를 주장하지 않는다.

기존 실패 원인을 실행으로 확인하되 명세를 바꾸거나 테스트를 약화해 녹색으로 만드는 수정은 하지 않는다. 실제 실패가 있으면 해당 case와 원래 오류를 보고한다. 전체 stage1/번역의 완료와 테스트의 통과는 별개다. 원래 WIP와 사용자의 로컬 index/branch는 reset/stash/checkout하지 않는다.
