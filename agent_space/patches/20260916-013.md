# 20260916-013 — Remove duplicate image-selection runtime mirrors

## Purpose
Continue the source-of-truth cleanup after `20260916-012` by removing the remaining image/asset runtime mirrors `activeImageId` and `activeAssetKind`.

The current authoritative state already exists elsewhere:

- project image identity/content is owned by `activeProject` / project-domain state;
- slot-to-image association is owned by `slot.imageId`;
- project-tree asset selection is owned by the application logic EFSM through `assetSelection` and `assetPath`.

`activeImageId` and `activeAssetKind` do not provide an independent domain meaning. They are written during slot/asset transitions, reset/swap/rollback, and project runtime capture/restore, but the Mantine frontend does not read them. Keeping them creates a second representation that must be manually synchronized with the actual SoTs.

## Ownership decision

- `appFSM.state.assetSelection` and `appFSM.state.assetPath` are the authority for project-tree selection.
- `slot.imageId` is the authority for image content assigned to a slot.
- `activeProject.images` is the authority for image models.
- `activeImageId` and `activeAssetKind` are redundant mirrors and are removed.
- `refreshImageControls()` is retained temporarily only as a compatibility-shaped read helper, but becomes side-effect-free and reads directly from the project model / selected slot instead of maintaining mirror state.

## Exact changes

1. Remove global `activeImageId` and `activeAssetKind` declarations.
2. Stop slot selection and slot type transitions from clearing those mirrors.
3. Stop slot reset and slot swap actions from clearing, snapshotting, or restoring those mirrors.
4. Remove the trash-path check that clears `activeImageId`; selected-asset invalidation already follows `machine.state.assetPath` and the existing `clearAssetSelection` transition semantics.
5. Remove `activeAssetKind` / `activeImageId` writes from `applyAssetSelectionAction()`; that action now updates only its authoritative `assetPath`, while the state-machine target continues to own `assetSelection`.
6. Convert `refreshImageControls()` from a mirror mutator into a pure lookup:

```js
function refreshImageControls(selected = getSelectedSlot()?.imageId) {
  return getProjectImage(selected) || null;
}
```

7. Remove the two mirrors from project runtime capture/restore/reset.

## Why this direction
The same facts were represented three ways: project/slot state, EFSM selection state, and mutable globals. Only the first two have defined ownership and consumers. The globals therefore add synchronization work without adding functionality.

The resulting dependency direction is:

```text
project image model / slot.imageId
            +
appFSM assetSelection / assetPath
            |
            v
frontend read helpers / UI
```

There is no reverse synchronization path into a second `activeImage*` or `activeAsset*` state.

## Rejected alternatives

- Keep `activeImageId` as a convenience cache: rejected because it is independently cleared/restored by multiple backend/core transitions and can diverge from `slot.imageId` or `assetPath`.
- Keep `activeAssetKind` synchronized with `assetSelection`: rejected because `assetSelection` already represents the same fact in the logic EFSM.
- Remove every `refreshImageControls()` call in this patch: rejected. The calls can be audited later as dead native-UI cleanup; making the helper pure removes the ownership problem without unnecessarily expanding this diff.
- Remove image renderer/model functions: rejected. Image rendering and project image state are functional domain/rendering responsibilities and are not part of the duplicate-mirror cleanup.
