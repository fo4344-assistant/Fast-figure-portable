# 20260831-008

## 목적

Mantine UI 리팩터링을 시작하기 전에 현재 Fast Figure shell, overlay, dashboard의 DOM 소유권을 분리하고 React 이관 경계를 확정한다.

## 변경 내용

- `agent_space/reviews/review-001.md`를 추가했다.
- 현재 toolbar/sidebar/overlay/dashboard의 책임을 분류했다.
- layout, label, caption, print, README를 사용자 작업 단위 기준으로 모두 controlled Mantine `Modal` 대상으로 확정했다.
- React가 toolbar/sidebar/modal shell을 하나의 tree로 소유하는 방식을 기본 이관 구조로 선택했다.
- Plotly/dashboard/slot drag-drop은 초기 Mantine 이관 범위에서 제외했다.
- 여러 portal을 기본 구조로 사용하지 않고, 특정 부분에서 shell 직접 이관이 불가능한 경우에만 임시 migration bridge로 허용했다.
- 첫 코드 패치의 범위를 React/Mantine runtime vendoring + 비가시 Provider bootstrap으로 제한했다.

## 이 방향을 선택한 이유

이번 Mantine 도입의 핵심 목적은 버튼 크기, 팝업 동작, focus, outside-click, stacking 같은 UI 공통 규칙을 다시 구현하지 않고 재사용하는 것이다.

shell UI를 React가 하나의 tree로 소유하면 MantineProvider와 UI 상태 바인딩의 경계가 명확해지고, static DOM과 React control을 같은 영역에서 장기간 혼합하는 구조를 피할 수 있다.

Plotly와 dashboard는 UI control보다 렌더링/interaction domain에 가깝고 현재 imperative 코드와 결합도가 높으므로 초기 UI 리팩터링에서 함께 재작성할 이유가 없다.

## 고려했지만 선택하지 않은 방향

- 모든 UI와 dashboard를 한 번에 React로 다시 작성하는 방향은 선택하지 않았다. Mantine 도입 목적과 무관한 Plotly/slot renderer 변경까지 포함되어 회귀 범위가 지나치게 커진다.
- 다중 portal을 기본 migration 구조로 사용하는 방향은 선택하지 않았다. legacy DOM, React root, portal mount, imperative sync, EFSM이 동시에 존재해 오히려 책임 계층이 늘어난다.
- layout/label/caption/print를 비모달 floating panel로 유지하는 방향은 선택하지 않았다. 실제 각 작업 흐름을 검토했을 때 뒤쪽 figure를 동시에 직접 조작해야 할 필요가 확인되지 않았다.
- 자체 `AppToolPanel`을 만드는 방향은 선택하지 않았다. Mantine가 이미 제공하는 modal interaction을 다시 구현하는 것이 되어 도입 목적과 충돌한다.

## 패치에 포함되지 않은 변경사항

애플리케이션 코드는 이 커밋에서 변경하지 않는다. React/Mantine dependency와 실제 UI 변경은 다음 커밋부터 단계적으로 적용한다.

패치 파일과 이 설명 파일 자체는 자기 자신을 재귀적으로 포함할 수 없으므로 diff 본문에는 포함하지 않았다.
