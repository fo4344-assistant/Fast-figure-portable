# 20261016-014 — Source Script r31 asset API 보완

## 목적·실제 변경

- 사용자 API 관련 보완 요청에 따라 r30 trace F3(공식 pure query 누락)와 F2의 asset create-and-select를 보완한다. 기존 API 의미와 계층 안에서 연결하며 새 public API/framework/authority를 만들지 않는다.
- 기준 `4871dc952bdfb291d79de28948918c1f587d4410` → 의미 변경 endpoint `b280a89b8e4b63b87538352c800db6689ddf8bf5`의 실제 `git diff --binary`가 같은 basename `.patch`다. Source 5개 파일, metadata, plan, 새 review를 포함한다. patch/설명 쌍은 자기 참조를 피하여 이 의미 endpoint 뒤에 추가한다.
- Source r31 fingerprint: `sha256:d2519623076e8dda860186f3532cc6dd45780e46bef6ec49cdea153dbd85254f`. current/open, closure_review null을 유지한다. 하위 lineage/내용은 갱신하지 않는다.

## 의미·책임·참조

- `assets.fileKind`와 `assets.resolveImportPlan`을 기존 project-api query registry에 등록하고 collisionModel과 함께 Application wrapper를 연결했다. Backend domain이 filename/MIME 분류와 current VFS collision/unique-path 계산을 소유한다.
- model/reservedPaths는 한 작업용 제안이며 query는 입력/Project/Frontend를 변경하거나 경로를 예약하지 않는다. stale replace는 available 분기보다 먼저 거부한다. ASSETS_IMPORTED의 commit 직전 current authority 재검증은 별도로 유지한다.
- 일반 `createEmptyProjectCsv` helper와 public `createEmptyProjectCsvAndSelect`를 구분한다. 생성 성공 뒤만 `selectProjectCsv`로 SELECT_ASSET을 요청한다. invalid CSV는 selection 전이를 일으키지 않는다. accepted SELECT_ASSET이 asset 선택/graph index clear를 함께 수행하므로 선행 CLEAR_GRAPH_OBJECT 전이는 없다.
- 성공 반환은 detached CSV, 생성 미commit은 기존 failure, 선택 거부는 none, throw는 전파한다. 이미 commit된 생성 뒤 선택/query 실패를 숨은 asset rollback이나 미commit으로 바꾸지 않는다. chart/object/slot을 selection 단계에서 변경하지 않는다.

## 선택 이유·기각 대안

- 별도 공개 계산 우회 route 대신 기존 query adapter/registry 사용: 미등록 operation 오류를 실제로 해소하고 동일 boundary에서 read-only 의미를 유지한다.
- UI model을 그대로 신뢰하거나 plan query를 commit으로 취급하는 방식 제외: collision choice 대기 이후 현재 asset이 바뀔 수 있다. 제안 identity와 current target의 일치가 필요하다.
- create helper에 숨은 Frontend 선택을 넣는 방식 제외: domain helper와 Application orchestration 책임을 혼합한다.
- 선택 전에 graph index부터 clear하는 방식 제외: invalid CSV 요청에서도 기존 선택이 일부 손실될 수 있다. 기존 SELECT_ASSET 전이가 두 runtime field를 함께 소유한다.
- 모든 public command를 bool/envelope로 획일화하는 방식 제외: F1의 다른 공개 반환값은 각 계약/소비자 대조가 필요하다.
- JS부터 고치는 방식 제외: Source-first 계층 순서를 보존한다. 하위 코드는 분류/계획/빈 CSV 선택의 호환성 자료로만 읽었다.

## 정적 검토·실행 구분

- 상세 producer/consumer·성공/실패/취소 시나리오: `agent_space/reviews/review-20261016-010-api-assets-r31-open.md`.
- canonical Git blob 기반 byte fingerprint 계산과 의미 endpoint의 `git diff --check`를 수행했다. 이는 Source Script/application 실행이 아니다.
- 실제 누적 patch의 reverse cached apply 확인 및 Actions 누적 version checker 결과는 아래 실행 기록에 남긴다. 완료 전 결과를 통과로 표현하지 않는다.
- 로컬 Source Script import/app/test/checker/build/TLC는 실행하지 않았다. helper/payload/temp는 현재 작업 디렉터리 내부 `.work/`만 사용한다.

## 전송·동일 commit 한계

- GitHub Contents API의 파일별 순차 PUT을 사용했다. 매 write에 현재 main HEAD와 blob SHA(새 파일은 404)를 확인하고 다음 HEAD로 진행했다. atomic multi-file commit이 아니다.
- Source와 metadata/patch가 같은 commit이어야 하는 조건을 Contents API로 충족했다고 주장하지 않는다. 실제 baseline→endpoint 누적 diff를 기록하고 baseline을 지정한 Actions 검사를 수행한다.
- 중간 Source-before-metadata push 검사 `38856891267` 등은 failure이며, metadata 반영 HEAD `1a5c6af5c7e878e4b8e8d03b39a2e007069c1b11`의 push 검사 `38856894439`는 success다. snapshot push 성공만으로 전체 누적 patch/semantic 검증을 주장하지 않는다.

## 제외·후속·닫힘 영향

- F1의 다른 mutation 공개 반환, F2의 다른 selection/zoom/runtime 완료, F4의 import router/export completion 및 전체 import/edit/export 왕복·purpose·duplicate-integration 검토가 남아 있다. 전체 API/Source closure는 open이다.
- 정책, PlusCal, verification model, JS/UI, browser tests, build/distribution은 수정하지 않았다. 하위 번역·regression/build/TLC 실행은 포함하지 않는다.
- Source-first 보완이며 하위 검증에서 닫힌 Source로 역전파한 변경이 아니다. 기존 r30은 open으로 기록돼 있었다. 이후 Source closure 후 PlusCal부터 전체 API query/selection 경로를 번역해야 한다.
