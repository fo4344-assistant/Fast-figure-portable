# 20260906-025 Mantine UI palette staging

## Purpose

Move the UI palette editor toward the single React + Mantine shell without creating a second persistent palette state or duplicating palette application rules.

## Current problem

The persistent palette already lives at `activeProject.appearance.uiPalette`, but the active legacy editor still reads values directly from DOM inputs through `uiPaletteFromControls()`. The legacy reset handler also writes every default color back into those DOM inputs before calling `applyUiPalette()`.

This makes the legacy controls part of the write path and prevents the staged Mantine shell from editing the same palette through a DOM-free command.

## Change

1. Add `uiPaletteFromValues(values)` as the common value normalizer using the existing `DEFAULT_UI_PALETTE` and `projectColor()` rules.
2. Keep `uiPaletteFromControls()` only as a legacy presentation adapter that collects the existing input values and delegates to `uiPaletteFromValues()`.
3. Add `applyUiPaletteFromValues(values, notify)` and `resetUiPaletteFromValues(notify)` so both Mantine and legacy UI use the same persistent palette object and the existing `applyUiPalette(false, notify)` renderer path.
4. Replace the legacy reset handler's repeated DOM assignments with `resetUiPaletteFromValues()`.
5. Expose the two DOM-free palette commands through `fastFigureUiBridge`.
6. Add `FastFigureUiPaletteStaging`, rendered with Mantine `ColorInput`, `Button`, `Group`, `SimpleGrid`, `Stack`, and `Text`.
7. The React component keeps only an unapplied draft. External/project palette changes refresh that draft from `snapshot.appearance.uiPalette`; applying commits through the shared command, while reset immediately restores the canonical defaults as the legacy reset did.

## Ownership

- Persistent source of truth: `activeProject.appearance.uiPalette` only.
- Palette validation/defaulting: `uiPaletteFromValues()` using the existing `projectColor()` and `DEFAULT_UI_PALETTE` rules.
- CSS variable projection and dashboard redraw: existing `applyUiPalette(false, notify)` path.
- Legacy inputs: presentation adapter only.
- Mantine local state: temporary edit draft only; not authoritative and not serialized.

## Preserved behavior

- Existing palette keys and default values are unchanged.
- Project import/export schema and `appearance.uiPalette` meaning are unchanged.
- Existing CSS custom properties and dashboard redraw behavior are unchanged.
- Existing legacy Apply behavior remains explicit.
- Existing Reset behavior still immediately restores defaults and applies them.
- No EFSM state names, transitions, domain algorithms, Plotly rendering rules, or file formats are changed.

## Rejected alternatives

### Keep a separate React palette state as the application state

Rejected because it would create two authorities and require bidirectional synchronization with the project object.

### Let Mantine write the legacy color inputs and click the legacy Apply button

Rejected because that preserves DOM as a write-path dependency and repeats the compatibility-host mistake corrected in the asset tree work.

### Reimplement CSS variable updates inside React

Rejected because `applyUiPalette()` is already the canonical projection from the project palette to CSS/dashboard rendering. Duplicating it would create inconsistent rendering rules.

## Risk

The main risk is draft synchronization when the project palette changes while the staged editor is mounted. The component therefore refreshes its draft when the serialized palette value changes. Because the current Mantine shell is still staging, this patch does not remove legacy controls or change active ownership.

## Rollback

Revert `20260906-025`. The previous legacy `uiPaletteFromControls()` and reset input assignments can operate independently of later Mantine staging. No data migration or file-format rollback is required.
