# 20260909-010 — Palette import error reporting correction

## 목적

`20260909-009`의 Mantine graph palette import에서 lifecycle wrapper가 예외를 내부에서 소비하는 현재 구조 때문에 parse/validation 실패가 사용자 status로 표시되지 않을 수 있는 문제를 교정한다.

## 변경 내용

- `FastFigureGraphPaletteActions.loadPalette()`의 `PALETTE_IMPORT` task 내부에 parse/validation/apply 전용 `try/catch`를 둔다.
- 실패 시 기존 legacy palette import와 동일하게 `팔레트 불러오기 실패: ...` status와 `graphPalette:load-error` debug log를 남긴다.
- status를 기록한 뒤 예외를 다시 throw하여 `appFSM.run()`이 lifecycle failure를 정상적으로 처리하게 한다.
- outer `try/finally`는 file input reset만 담당한다.

## 선택 이유

공통 `runLifecycleTask()`는 lifecycle 오류를 로깅한 뒤 catch하여 호출자에게 다시 throw하지 않는다. 이 동작은 다른 import/export 경로에서도 공통 wrapper 계약으로 사용되므로 wrapper 자체를 바꾸는 것은 범위가 과도하다. palette task 안에서 해당 기능의 사용자 오류 표시를 책임지는 것이 가장 좁고 기존 동작과 일치한다.

## 기각한 대안

1. **`runLifecycleTask()`가 항상 예외를 다시 throw하도록 변경**
   - project/slot/asset import 등 기존 모든 호출 경로의 오류 계약을 바꾸므로 이번 교정 범위를 벗어난다.

2. **lifecycle을 거치지 않고 palette import를 직접 실행**
   - 기존 `PALETTE_IMPORT` lifecycle 의미를 잃으므로 기각했다.

3. **오류를 status만 표시하고 rethrow하지 않음**
   - lifecycle failure가 성공처럼 종료될 수 있어 기각했다.

## 상태 권한과 경계

- palette authority와 mutation 경계는 `20260909-009`와 동일하다.
- 이번 패치는 오류 전달/표시만 교정하며 project/chart 상태 구조를 바꾸지 않는다.

## 검증

- 잘못된 JSON 파일에서 사용자 status에 parse 오류가 표시된다.
- `colors`가 없거나 유효한 HEX가 없을 때 각각 오류 status가 표시된다.
- 오류 뒤 file input이 비워져 같은 파일을 다시 선택할 수 있다.
- lifecycle은 failure 후 공통 경로에 따라 복구 가능해야 한다.
- 정상 palette import 동작은 `009`와 동일해야 한다.

## 롤백

`loadPalette()`의 task 내부 `try/catch`를 제거하고 `009`의 outer catch 형태로 되돌리면 된다. 다른 파일이나 상태 모델에는 영향이 없다.
