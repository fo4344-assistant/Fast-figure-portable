# Mantine-owned sidebar resize/collapse

## 목적

현재 Mantine shell은 `AppShell.Navbar` 폭을 370px로 고정하고 있어 기존 sidebar의 두 기능인 collapse와 360–620px drag resize가 Mantine UI에서 빠져 있다. 이 패치는 shell/navigation 자체의 UI 소유권을 Mantine 쪽으로 더 옮기되 project state, EFSM, renderer 의미에는 손대지 않는다.

## 변경 내용

대상은 `fast-figure-ui.js` 하나다.

- `FastFigureShell`에 React local UI state를 추가한다.
  - `navbarWidth`: 초기 370px.
  - `navbarCollapsed`: 초기 false.
  - `navbarDragRef`: 현재 resize pointer id만 보관하는 일시 상태.
- 기존 legacy sidebar 범위와 동일하게 폭을 360–620px로 clamp한다.
- header에 Mantine `Button` 기반 sidebar 표시/숨김 제어를 추가한다.
- `AppShell.navbar.collapsed`를 직접 사용하여 desktop/mobile navbar를 접고 펼친다.
- `AppShell.Navbar` 오른쪽에 pointer-capture 기반 세로 resize separator를 둔다.
- resize 중에는 기존과 동일하게 body text selection을 막고 `col-resize` cursor를 사용한다.
- width/collapse 변경 뒤 기존 `syncLayoutMapSize()`와 `schedulePlotResize()`를 재사용해 retained layout/Plotly renderer가 새 shell geometry를 반영하도록 한다.
- resize 완료 시 `mantine:sidebar-resize` debug event를 남긴다.

## source of truth / 상태 경계

sidebar 폭과 collapse는 project/domain 영속 상태가 아니다. 따라서 새 project object나 EFSM region을 만들지 않고 `FastFigureShell`의 React local UI state만 사용한다.

- project/model authority: 변경 없음.
- `appFSM`: 변경 없음.
- layout/slot/chart/image state: 변경 없음.
- React local state는 shell 표시 상태와 pointer id만 가진다.
- Plotly/layout geometry 계산은 기존 함수가 계속 담당한다.

legacy `installSidebarControls()`의 `.app`/`aside` 상태를 Mantine state에 연결하거나 양방향 동기화하지 않는다. 즉 새 migration store/bridge는 만들지 않는다. legacy sidebar controller는 아직 전체 cutover 전이므로 그대로 남지만 Mantine `AppShell`의 width/collapse authority에는 참여하지 않는다.

## 선택 이유

`review-010-mantine-ui-inventory.md`는 shell/sidebar resize/collapse를 Mantine shell이 보존해야 할 기능으로 기록한다. 현재 `AppShell`이 이미 generic shell을 소유하므로, 이 기능을 React local state로 구현하는 것이 가장 짧고 책임 경계가 명확하다.

기존 `installSidebarControls()`는 `.app`, legacy `aside`, `#sidebarResizer`, `#sidebarToggle`을 직접 조작하므로 Mantine에서 이를 호출하거나 값을 읽으면 `Mantine -> legacy DOM bridge`가 된다. 이번 구현은 그 경로를 만들지 않고 `AppShell` API를 직접 사용한다.

## 고려했지만 선택하지 않은 방향

### 1. Mantine 버튼에서 `#sidebarToggle.click()` 호출

기각했다. legacy DOM event를 Mantine shell의 기능 command처럼 사용하는 migration bridge가 생기고 최종 제거 시 다시 뜯어내야 한다.

### 2. legacy CSS variable `--sidebar-width`를 Mantine에서도 source로 사용

기각했다. legacy `.app` CSS state와 React `AppShell` state가 같은 사실을 독립적으로 소유하거나 동기화해야 하므로 source-of-truth 규칙에 맞지 않는다.

### 3. sidebar 폭/collapse를 project 또는 appFSM에 추가

기각했다. 이는 영속 project 의미나 기능 EFSM 전이가 아니라 shell-local 표시 상태다. 새 상태 계층을 추가하면 복잡도만 증가한다.

### 4. 기존 dynamic `aside.scrollWidth` 최소폭 계산을 그대로 이식

이번 패치에서는 넣지 않았다. legacy sidebar는 고정 HTML form의 scroll width를 측정해야 했지만 Mantine form controls는 navbar 폭에 맞춰 layout되는 구조이고 inventory가 요구하는 기존 하한 360px은 그대로 보존한다. 실제 Mantine controls에서 360px보다 큰 최소폭이 필요하다는 회귀가 확인되면 AppShell navbar ref를 기준으로 별도 검토한다.

## EFSM / domain 영향

없음.

- `APP_STATE_DEFINITIONS` 변경 없음.
- `ApplicationStateMachine` 변경 없음.
- project mutation 없음.
- FFPX/FFSX/Plotly 의미 변경 없음.
- slot/image/layout/label/caption/export 알고리즘 변경 없음.

## 재사용한 기존 기능

- `syncLayoutMapSize()`
- `schedulePlotResize()`
- `debugLog()`
- 기존 legacy sidebar의 370px 초기값, 360px 최소, 620px 최대 범위

## 검증

자동 workflow에서 다음을 통과해야 한다.

1. `git apply --check`
2. `git diff --check`
3. `node --check fast-figure-ui.js`
4. portable HTML build
5. split/portable `file://` smoke

수동 회귀 확인 항목:

1. 초기 navbar 폭이 370px인지.
2. header의 sidebar 버튼으로 navbar가 완전히 접히고 다시 열리는지.
3. 접힘/펼침 뒤 dashboard Plotly가 남은 폭에 맞게 resize되는지.
4. 오른쪽 separator drag 시 360px 아래/620px 위로 넘어가지 않는지.
5. drag 중 text selection이 발생하지 않고 pointer release/cancel 뒤 cursor/user-select가 복구되는지.
6. resize 후 layout overlay/map geometry가 새 main 영역에 맞는지.
7. project/slot/asset selection 및 import/export state가 sidebar UI state와 독립적인지.

## 위험과 후속 작업

- legacy `installSidebarControls()`는 아직 source에 남는다. 이번 패치는 Mantine shell 기능 누락을 채우는 단계이며, 전체 UI functional-equivalence 확인 전 legacy generic UI를 대량 제거하지 않는 `plan-006` 원칙을 따른다.
- legacy controller와 Mantine controller 사이에 동기화는 없다. 최종 shell cutover 시 legacy `.app` sidebar markup/CSS/controller를 제거해야 한다.
- CSV header line 수는 검토 중 legacy graph/data preview renderer와 결합되어 있음을 확인했다. 임시 DOM-value bridge를 만들지 않기 위해 이번 패치에서 다루지 않았고, graph/data form ownership 단위에서 함께 처리한다.
