# 20261001-030 — 고수준 명세와 저수준 구현 경계 명확화

## 변경 요구

사용자가 개발 단계의 의도를 다음과 같이 명확히 했다.

- Source Script는 대상 언어·디바이스 종속 저수준 알고리즘을 생략한다.
- PlusCal/TLA+ 검증 모델은 Source Script의 고수준 알고리즘이 실행 가능한 구조인지 검증한다.
- source code 단계에서 실제 언어·OS·디바이스에 맞는 저수준 알고리즘을 작성한다.
- source code 단계는 새로운 고수준 알고리즘을 추가 개발하는 단계가 아니다.
- 데이터 형태·종류, 파일 위치·경로·확장자, schema, contract 구조처럼
  고수준 의미에 필요한 정보는 저수준 구현으로 간주해 생략해서는 안 된다.

기존 v0.2.0에는 대상 언어 타입·메모리·라이브러리를 뒤 단계로 남긴다는 규칙은 있었지만,
이 경계가 충분히 구체적이지 않아 파일/스키마/데이터 계약까지 구현 세부로 오인할 여지가 있었다.

## 변경 내용

### Source Script

새 `고수준 알고리즘과 저수준 구현의 경계` 절을 추가했다.

Source Script에서 구체 구현을 생략할 수 있는 예:

- memory allocation/layout/buffer strategy
- language ownership primitive
- thread/mutex/atomic/event-loop primitive
- OS/browser/device API와 syscall
- concrete filesystem/network plumbing
- 특정 library 호출 문법
- SIMD/GPU/device-specific optimization
- 대상 언어 class/generic/exception representation

반대로 다음은 고수준 의미에 필요하면 반드시 Source Script에 남긴다.

- 데이터 형태·종류·필드·관계
- schema와 contract
- 논리적 file/package 위치와 문서 구조
- 의미 있는 filename/path/extension/MIME/format
- serialization에서 보존할 관계
- encoding/container/path constraint
- 외부 입력/출력 허용 조건
- ID/reference/key/path 관계
- 처리 순서와 transaction/commit/failure 의미
- 외부 resource의 고수준 read/write 의미
- correctness에 영향을 주는 lock/order/stale-read/resource-lifetime 요구

판별 기준을 다음처럼 명시했다.

```text
대상 언어와 디바이스를 바꿔도 유지되는 의미
→ Source Script

같은 고수준 의미를 보존하면서 환경에 맞게 선택할 수 있는 실행 기법
→ source-code 구현 단계
```

### PlusCal/TLA+

검증 모델이 기존 pseudocode의 역할을 대체한다는 점을 명시했다.

완성된 모델을 보고 구현할 때:

- 새로운 고수준 알고리즘을 설계하지 않음
- branch/order/state/reference/transaction/failure 의미를 새로 결정하지 않음
- data/schema/file/package contract를 다시 추론하지 않음
- 실제 target language/device의 저수준 실행 기법만 추가함

Source Script에서 생략한 저수준 알고리즘은
PlusCal/TLA+에서도 실제 platform 구현으로 확정할 필요가 없지만,
고수준 알고리즘이 그 기능을 호출해도 문제가 없는지 검증할 수 있도록
interface/precondition/result/failure/atomicity/environment assumption을 모델링하도록 했다.

저수준 operation을 abstract action으로 만들 수는 있어도
그 operation을 호출하는 고수준 알고리즘 전체를 단순 success action 하나로 치환해서는 안 된다.

### Source code

source code 단계의 역할을:

```text
검증된 고수준 알고리즘
+
target language / OS / device에 맞는 저수준 구현
```

으로 한정했다.

Source Script와 verification model에서 이미 정한:

- data shape
- schema
- file/package contract
- reference relation
- algorithm order
- transaction/failure semantics

는 구현 편의를 위해 재설계하지 않는다.

## 정책 버전

`source-script-policy.md`:

- v0.2.0 → v0.2.1

개발 단계 자체를 다시 바꾸는 것은 아니고,
v0.2.0에서 도입한 formal verification 흐름의 고수준/저수준 경계를 명확히 하는 변경이므로 patch-level revision으로 올렸다.

## 선택 이유

Source Script가 platform-independent하다는 사실과
파일 형식·스키마·데이터 계약을 생략해도 된다는 주장은 서로 다르다.

예를 들어:

```text
ZIP library API 사용법
→ 저수준 구현

package 안에 어떤 entry/document가 있고
어떤 data를 소유하며 어떤 path가 허용되는지
→ 고수준 contract
```

를 구분해야
대상 언어만 바꾼 구현에서도 동일한 file format과 domain semantics를 보존할 수 있다.

## 고려했지만 선택하지 않은 방향

### Source Script에 실제 platform I/O algorithm까지 포함

선택하지 않았다.

그렇게 하면 Source Script가 특정 target language/device에 종속되어
다른 환경 구현의 공통 원천 역할을 잃는다.

### 파일·schema·extension도 구현 세부로 전부 뒤로 미룸

선택하지 않았다.

이 정보는 interoperability, reference resolution, validation과 algorithm branch를 결정할 수 있어
고수준 의미의 일부다.

### PlusCal/TLA+에 실제 OS/library 호출까지 모델링

선택하지 않았다.

검증 모델의 목적은 특정 API 구현을 재현하는 것이 아니라
고수준 알고리즘이 필요한 저수준 capability와 결과를 이용해 일관되게 실행 가능한지 검증하는 것이다.

## 기존 project 상태 영향

정책 문서만 변경한다.

- Source Script r12 content/revision/fingerprint 변경 없음
- verification-model r1 content/revision/fingerprint 변경 없음
- source code 변경 없음

다만 이후 verification-model coverage를 판단할 때는
이번 v0.2.1의 경계를 적용한다.

즉 현재 r1에서 생략된 항목도 단순히 platform-specific이라는 이유로 생략할 수 없고,
Source Script에 존재하는 고수준 algorithm/data/schema/file contract라면
최종 verification-model이 source-code 구현 전에 충분히 연결해 표현해야 한다.
