# 20260907-052 — Mantine project-name editor

## Purpose

Port the project-name editor into the Mantine project section without introducing a legacy DOM bridge or a new state owner.

The existing project model remains authoritative. Mantine only presents and edits `activeProject.projectName` using the same normalization rules as the legacy input.

## Scope

Only `fast-figure-ui.js` is modified.

No changes are made to:

- `fast-figure.js`
- `ProjectObject` / project model structure
- FFPX import/export format
- UI FSM or functional EFSM definitions
- legacy `#projectName` input before final cutover

## Existing behavior reused

The legacy project-name editor already defines the behavior that must be preserved:

- while typing: `slice(0, 120)`
- on committed change: `trim().slice(0, 120)`
- normalized value is written back to the control
- `debugLog("project:name", { projectName })` is emitted on commit

The Mantine editor writes to the same `activeProject.projectName` model property and does not create a parallel persistent React state value.

## Exact changes

1. Adds a Mantine `TextInput` labeled `프로젝트 이름` to `FastFigureProjectActions`.
2. Uses the current `activeProject.projectName` as the uncontrolled input's `defaultValue`.
3. Uses a key derived from the authoritative project-name value so a model-level project replacement/import can refresh the uncontrolled input when the component rerenders.
4. `onChange` updates `activeProject.projectName` with the existing 120-character limit.
5. `onBlur` applies the existing trim + 120-character normalization, writes the normalized value back into the input, and emits the existing `project:name` debug event.
6. The editor is disabled while the UI lifecycle is not `ready`, matching the other Mantine project controls' busy policy.
7. No `document.getElementById("projectName")`, legacy click, or synchronization bridge is introduced.

## State ownership

Persistent project-name state remains owned exclusively by `activeProject` / the project model. React owns only the input element's transient browser editing state between events.

## Why this direction

A controlled React copy would create a second project-name state owner and require synchronization logic after project import. An uncontrolled Mantine input with direct model updates preserves the existing ownership model while still letting imports refresh the field on the next application-state render.

## Rejected alternatives

### Reading/writing the legacy `#projectName` input

Rejected because that would make legacy DOM an internal API for Mantine.

### Adding a Mantine-specific project-name state to the UI FSM

Rejected because the project name is persistent project data already owned by the project model, not transient UI state.

### Adding a new EFSM event solely for text editing

Rejected because the existing architecture already permits this project metadata property to be edited directly and no functional transition is gained by duplicating it.

### Maintaining a controlled React `useState` mirror

Rejected because it would require bidirectional synchronization and increase state ownership complexity without adding capability.

## Rollback

Revert `20260907-052.patch`. The legacy project-name editor remains untouched until final cutover.
