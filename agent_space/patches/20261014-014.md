# 20261014-014 — Refine plan 014 after frontend appFSM review

## 목적과 변경 내용

`plan-014.md`의 renderer invalidation 설계를 현재 React/Mantine frontend와 appFSM 구조를 다시 대조한 결과에 맞게 수정한다.

주요 변경:

- `#ff-react-bootstrap-root`와 `#dashboard`의 DOM ownership 분리를 명시.
- workspace action 직후가 아니라 `appFSM.send()` 반환 뒤가 renderer 갱신 가능한 안전한 시점임을 명시.
- 기존 `appFSM.subscribe() → useSyncExternalStore` state publish contract를 renderer invalidation에 재사용하지 않음.
- ApplicationStateMachine 내부에 새 completion listener registry를 추가하는 초기안 기각.
- UI/API orchestration helper가 `appFSM.send()` 반환 뒤 projection invalidation을 한 번 적용하는 방식으로 변경.
- `useSyncExternalStore` snapshot identity 조건을 별도 검토 항목으로 추가.
- lifecycle transition과 renderer invalidation 분리.
- 여러 `appFSM.send()`를 묶는 기존 composite command를 이번 변경에서 event별 full render로 해체하지 않음.
- target event는 우선 `PROJECT_NODE_MOVED`, `PROJECT_TRASH_EMPTIED`로 제한하고 `SLOTS_SWAPPED`은 regression 후 공통 helper로 이동 여부를 결정.
- delegated dashboard listener와 async Plotly render generation의 안전 조건을 검증 항목에 추가.

## 재검토 결과

현재 Mantine AppShell은 dashboard slot DOM을 React child로 소유하지 않는다. 따라서 `renderDashboard()`의 child DOM 재생성과 React VDOM이 동일 node를 경쟁해서 수정하는 구조는 아니다.

반면 `appFSM.send()`는 workspace action 뒤 graphObject/assetSelection reconciliation을 추가로 수행할 수 있으므로 mutation action 내부에서 즉시 `renderDashboard()`를 호출하면 최종 selection state보다 앞선 projection을 만들 위험이 있다.

`appFSM.send()`는 동기 함수이므로 호출자가 반환을 받은 시점에는 handled region action/transition/reconciliation/publish가 끝나 있다. 이번 문제 범위에서는 appFSM 내부 completion system을 새로 추가하기보다 이 기존 경계를 이용하는 것이 최소 복잡도다.

## useSyncExternalStore 검토

React store snapshot은 `appFSM.state` 객체 identity다.

현재 target event:

- `PROJECT_NODE_MOVED`, `PROJECT_TRASH_EMPTIED`: direction payload로 새 state object 생성.
- `SLOTS_SWAPPED`, `GRID_LAYOUT_CHANGED`: selection reconciliation action이 새 immutable state object 생성.
- `notify()`: revision 증가로 새 state object 생성.

따라서 현재 trash 문제는 React store snapshot 갱신 누락이 아니라 dashboard DOM projection 누락이다.

다만 future event에서 project mutation과 React projection 변경이 있는데 snapshot identity가 바뀌지 않는 경우 renderer helper로 숨기지 않고 별도 app-state notification 의미를 설계해야 한다.

## 선택 이유

ApplicationStateMachine에 renderer completion infrastructure를 추가하면 현재 문제보다 더 넓은 state-machine contract를 바꾸게 된다.

반대로 UI/API orchestration helper는:

- 기존 FSM publish semantics 유지.
- React store contract 유지.
- mutation과 renderer 책임 분리.
- final selection reconciliation 이후 current authority를 읽음.
- 이번에 확인된 누락 event만 최소 적용 가능.

이라는 장점이 있다.

## 기각한 방향

- `publish()` subscriber에서 full render: 한 send에 여러 publish가 발생할 수 있어 중복 render 위험.
- workspace mutation action 안에서 render: 뒤쪽 selection reconciliation 이전이라 순서가 잘못될 수 있음.
- ApplicationStateMachine 내부 completion listener 추가: 현재 문제 해결에 비해 구조 변경 범위가 큼.
- 모든 기존 mutation을 즉시 새 helper로 이전: composite command의 중간 상태 render와 Plotly 중복 재생성 위험.
- renderer helper로 React snapshot identity 문제까지 보정: 서로 다른 책임을 숨기므로 기각.
