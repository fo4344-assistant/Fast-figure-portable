## 목적·변경

실필드 테스트에서 확인한 문제에 대해 관련 Source Script의 구체적인 수정방안을 포함한 보완 계획을 작성한다.

추가 대상은 `agent_space/plans/plan-028.md`와 본 설명 문서뿐이다. 기준 commit은 `9e58bdf0381b62bb59068a44ca78d75be6edcaed`다. 실제 파일로 native Git diff를 생성하며 패치 자신은 자기참조를 피하려고 payload에서 제외한다.

## 선택한 방향·이유

객체 추가와 FFSX 불러오기의 두 재현 증상을 선택 슬롯의 raw state와 공식 read projection 혼동이라는 공통 경계 문제로 다룬다. Source Script → pseudocode → source code 순서의 계획으로 구성하고, Source Script 파일별 입력·반환 구조·owner·publication·이벤트 시점 ID 취득·비동기 target 고정·none/ID 0·거부와 실패를 구체화했다.

기존 InterfaceStateMachine과 Application facade를 재사용하고 별도 selection authority나 신규 public API를 전제하지 않는다. external-store snapshot의 안정성도 계획에 포함해 매번 새 readState 객체를 반환하도록 getter만 치환하여 render loop를 만드는 수정을 피한다. 두 재현 지점 밖의 동일 소비자는 정적 영향 후보로 구분했다.

## 고려했지만 선택하지 않은 방향

- 즉시 코드 수정: 이번 요청은 계획 문서 작성이며 구현은 별도 지시와 구분한다.
- 두 callback만 국소 수정: 공식 read/subscribe 계약과 다른 동일 소비자의 불일치를 남긴다.
- raw state에 selectedSlotId 독립 복사: owner와 mirror의 이중 authority가 된다.
- Backend가 UI 선택을 암묵적으로 읽거나 누락 ID를 0으로 보충: explicit target과 Backend current validation을 훼손한다.
- 기존 UI 실패를 API 성공으로 대체: 수정 후 실제 사용자 동작의 증거가 되지 않는다.
