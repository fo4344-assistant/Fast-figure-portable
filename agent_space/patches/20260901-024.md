# 20260901-024 — Mantine 파일 선택 staging 경계

## 목적과 변경 내용

`plan-003.md`의 Commit B를 이어서 파일 추가 UI를 inactive `FastFigureSidebarStaging`에 Mantine `FileButton`으로 준비한다.

- 현재 슬롯 유형에 따른 파일 선택 라벨, `accept`, 다중 선택 여부, 안내문을 `projectFileInputModel()`에서 한 번만 계산한다.
- legacy `syncSlotContentTypeUi()`도 이 모델을 사용해 기존 native file input의 라벨/accept/안내문을 동기화한다.
- 기존 `$("file").onchange` 안에 있던 실제 파일 분기 처리를 DOM-독립 `loadProjectFiles(fileList)`로 추출한다.
- legacy native input과 Mantine staging `FileButton`이 모두 같은 `loadProjectFiles()`를 호출한다.
- bridge에는 상태를 저장하지 않는 `readFileInput()`과 `loadFiles(files)`만 추가한다.
- 앱 버전을 `1.1.53-alpha`로 올린다.

## source of truth 검토

새로운 영속 상태나 React local state를 만들지 않는다.

- 슬롯의 콘텐츠 유형은 기존 slot/domain model의 `contentType`이 계속 source of truth다.
- 슬롯 미선택 상태의 기본 유형은 기존 `pendingSlotContentType`이 계속 source of truth다.
- `projectFileInputModel()` 결과는 현재 슬롯 상태에서 즉시 계산되는 renderer용 파생값이며 저장하거나 다시 동기화하지 않는다.
- `File` 객체는 사용자가 이번 파일 선택 동작에서 전달한 입력값으로만 사용하며 프로젝트 상태의 복사본으로 보관하지 않는다.
- 프로젝트 CSV/image의 실제 저장과 슬롯 연결은 기존 `loadDataFile()`, `loadImageFile()`, `loadFileIntoSlot()` 및 그 내부 EFSM 이벤트가 계속 담당한다.

## 이 방향을 선택한 이유

현재 파일 추가 기능의 도메인 로더는 이미 데이터/이미지/슬롯 단위 함수로 분리되어 있다. Mantine 전환을 위해 필요한 것은 native `<input type="file">`의 `change` 이벤트에 묶여 있던 최상위 분기만 분리하는 것이다.

Mantine `FileButton`을 사용하면 최종 shell에서 별도 hidden input ID와 `element.click()` 수명주기를 직접 관리할 필요가 없다. 동시에 legacy UI가 활성인 동안에는 기존 native input이 같은 도메인 명령을 호출하므로 Commit C 전까지 동작 경로가 갈라지지 않는다.

파일 선택기의 라벨/accept/안내문도 같은 파생 함수에서 계산하게 하여 legacy와 staging이 서로 다른 규칙을 갖지 않도록 했다.

## 고려했지만 선택하지 않은 방향

### Mantine 버튼에서 기존 `$("file").click()` 호출

선택하지 않았다. 구현 규모는 작지만 React/Mantine shell이 legacy DOM ID에 계속 의존하게 되어 cutover 후 제거해야 할 결합을 새로 만드는 방향이다.

### React state에 선택된 File/FileList 저장

선택하지 않았다. 파일은 즉시 기존 로더로 전달하면 충분하며, 별도 상태에 보관할 기능적 이유가 없다. 프로젝트 에셋과 파일 객체 사이의 두 번째 권위 상태도 만들 필요가 없다.

### `loadDataFile()` / `loadImageFile()`를 React용으로 재작성

선택하지 않았다. 해당 함수들은 이미 프로젝트 모델과 EFSM 전이를 사용하고 있으므로 UI migration을 이유로 중복 구현하면 회귀 가능성과 복잡도만 증가한다.

### CSV/image 세부 설정 패널까지 같은 패치에서 전환

선택하지 않았다. 헤더 줄 수, 빈 이미지 삽입, 이미지 fit/scale/position은 각각 별도의 도메인 쓰기 규칙을 확인해야 한다. 파일 입력 경계를 먼저 공통화한 뒤 후속 패치에서 해당 컨트롤을 옮기는 편이 책임 경계가 명확하다.

## 호환성과 동작 보존

- 이미지 슬롯에서는 기존과 동일하게 첫 번째 파일만 로드한다.
- 그래프 슬롯에서는 기존과 동일하게 선택된 파일들을 데이터 파일로 순차 로드한다.
- 슬롯이 선택되지 않은 경우 기존 `slotFileKind()` 판정으로 데이터와 이미지를 프로젝트 에셋으로 추가한다.
- legacy native input은 처리 후 값이 비워져 같은 파일을 다시 선택할 수 있는 기존 동작을 유지한다.
- 파일 형식 오류와 로딩 오류 메시지는 기존 `status()` 경로를 유지한다.

## 후속 작업 / 범위 밖

- legacy `filePick`, hidden `file` input, `syncSlotContentTypeUi()`의 DOM 처리 자체는 Commit C/D 전까지 유지한다.
- `csvSelectionPanel`, `imageSelectionPanel`, `headerLines`, `insertEmptyImage` 및 이미지 세부 설정은 후속 Commit B 패치에서 도메인 계약을 확인한 뒤 Mantine로 옮긴다.
- staging shell은 계속 비활성 상태이며 사용자에게 보이는 UI 소유권은 아직 바꾸지 않는다.
