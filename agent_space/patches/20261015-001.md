# 20261015-001 — Source Script r24 Backend / Application boundary / Frontend 분리

## 목적

`agent_space/plans/plan-016.md`의 첫 구현 단계인 Source Script architecture patch를 적용한다.

r23에서는 Project EFSM과 interface FSM의 상태 책임 자체는 분리되어 있었지만 Frontend FSM과 renderer가 Backend authoritative state를 직접 읽고, Source Script logical module hierarchy가 Backend/Frontend 경계를 표현하지 않았다. `review-20261014-019-plan-016-boundary-audit.md`에서 이 직접 dependency와 SELECT_SLOT의 조건부 persistent mutation, read-time live normalization 가능성, 혼합 물리 파일의 논리 책임 미정 문제를 확인했다.

이번 r24는 기존 ProjectObject schema나 domain algorithm을 바꾸는 것이 아니라 Backend와 Frontend 사이의 공식 command/query/result 경계를 Source Script의 Module decomposition hierarchy로 확정한다.

## 실제 변경

### system.py

- system의 직접 논리 하위를 Backend / Application boundary / Frontend / Portable build로 재정의했다.
- physical file hierarchy와 logical Module decomposition을 분리했다.
- Backend↔Frontend cross-layer access는 API/Adapter를 통해서만 허용하도록 명시했다.
- `portable_build.py`는 Backend/Frontend의 자식이 아니라 system-level packaging responsibility로 유지했다.
- startup도 Application boundary가 initial Backend projection과 Frontend lifecycle을 연결하고 renderer에는 public actions/read projection만 전달하도록 정리했다.

### project_state.py

- `activeProject`, `projectObjects`, `projectVfs`를 Backend 내부 state/helper로 명시했다.
- `BACKEND_QUERY_KINDS`, `BACKEND_READ_BOUNDARY_RULE`을 추가했다.
- `FrontendValidatedInput`, `FrontendReconciliationInput` contract를 정의했다.
- `readBackendProjection`, `validateFrontendIntent`, `buildFrontendReconciliationInput`의 고수준 query/validation/reconciliation 의미를 정의했다.
- read-time normalization은 live ProjectObject가 아니라 projection/candidate copy에서만 수행하도록 명시했다.

### project_efsm.py

- Project EFSM을 Backend 내부 persistent mutation controller로 명시했다.
- Frontend component/FSM/renderer direct call을 공식 route로 인정하지 않도록 했다.
- 누락된 `slots.swap → SLOTS_SWAPPED` route를 추가했다.
- 기존 SELECT_SLOT의 `pendingContentType` 의미를 잃지 않도록 `slots.select.pendingContentType → SLOT_TYPE_CHANGED` route를 명시했다.
- ProjectMutationResult는 Application boundary에 반환되고 Backend가 Frontend FSM/renderer를 직접 호출하지 않는다고 명시했다.

### interface_fsm.py

- `activeProject` direct import를 제거했다.
- Backend identity를 직접 resolve하지 않고 Application boundary가 검증한 input만 소비하도록 변경했다.
- post-commit reconciliation도 Backend를 직접 조회하지 않고 `FrontendReconciliationInput`만 소비하도록 했다.
- Backend task callback을 실행하던 `run(..., task)` 책임을 제거했다.
- Application boundary가 현재 Frontend references를 읽을 수 있도록 immutable `readState()` 의미를 추가했다.

### application_fsm.py

- 이 물리 파일의 논리 책임을 third FSM이 아닌 Application boundary adapter/orchestrator로 확정했다.
- `dispatchProjectQuery`를 Backend read/query 경계로 정의했다.
- Backend reference validity가 필요한 SELECT_SLOT/SELECT_ASSET/SELECT_GRAPH_OBJECT만 validation query를 수행하고 overlay/Escape/lifecycle 같은 Frontend-only event는 불필요한 Backend query를 만들지 않도록 했다.
- `dispatchSlotSelection`에서 SELECT_SLOT transition과 optional `SLOT_TYPE_CHANGED` persistent command를 명시적으로 분리했다.
- Project commit 성공 뒤에만 Backend reconciliation query → Frontend reconciliation → renderer projection input 순서가 이어지도록 했다.
- import/export lifecycle task 실행을 Frontend FSM에서 Application boundary로 이동했다.

### api_ui.py

- `activeProject`와 `selectedSlotId` direct import를 제거했다.
- FastFigureApi를 Backend mutation, Backend query, Frontend runtime event의 public cross-layer contract로 강화했다.
- `slots.swap` public mutation 의미를 추가했다.
- `slots.select`가 validated Frontend selection과 optional persistent contentType command를 조정하는 Application operation임을 명시했다.
- Mantine lifecycle helper는 Backend task를 interfaceFSM에 넘기지 않고 Application lifecycle adapter를 사용하도록 했다.

### renderer_runtime.py

- `activeProject`, `interfaceFSM`, `selectedSlotId`, application dispatch direct import를 제거했다.
- renderer input을 immutable Backend `projectProjection`, final Frontend `interfaceState`, public `frontendActions`로 정의했다.
- dashboard/style/chart/workspace/startup projection이 supplied projection만 읽도록 변경했다.
- slot selection, slot swap, file-drop target preparation은 public frontend/API action surface를 통해 수행하도록 했다.
- renderer는 read-time normalization이나 DOM/Plotly state를 Backend authority에 되돌려 쓰지 않는다.

### assets_files.py / graphs.py / layout_annotations_export.py

- 한 물리 파일 안의 Backend domain calculation과 Application-boundary wrapper를 논리적으로 구분하는 responsibility/boundary rule을 추가했다.
- Backend calculation이 Application adapter를 역호출하거나 Frontend selection을 직접 읽지 않도록 했다.
- graph public wrapper는 필요한 `slotId/chartId/csvId`를 explicit input으로 받도록 고수준 signature를 명확히 했다.
- image/label wrapper는 `selectedSlotId` direct import 대신 explicit `slotId`를 입력으로 받도록 했다.
- `layout_annotations_export.py`에서 Frontend `selectedSlotId` import를 제거했다.

### closure와 lineage

- `review-20261015-020-sourcescript-closure-r24.md`에서 논리적 완결성, 프로젝트 목적 부합, 중복/통합 검토를 각각 근거와 함께 닫았다.
- Source Script fingerprint를 `sha256:f4717433f5dd4111d9a2644b7cc5d66a9abb25fb477892eafde23d9b964ac5d3`로 갱신했다.
- Source Script를 r24 / current / closed로 기록했다.
- 기존 pseudocode r10, verification-model r24, Source Code r29는 r23 lineage이므로 모두 `stale`로 전환했다.
- 기존 verification의 TLC `pending`은 그대로 두었으며 r24 검증 결과로 취급하지 않았다.

## 선택한 방향과 이유

새 project store, Frontend ProjectObject mirror, command bus 또는 combined FSM을 만들지 않았다.

이미 존재하는 `activeProject`, Project EFSM, FastFigureApi, application orchestration, ProjectMutationResult를 확장해 cross-layer boundary를 구성하는 것이 같은 기능 자유도를 가장 적은 중복 구조로 달성한다.

읽기는 Project EFSM command로 강제하지 않았다. 정책상 calculation/read와 authoritative mutation은 같은 path일 필요가 없으며, plan-016의 요구는 Frontend가 Backend 내부를 직접 읽지 않는 것이다. 따라서 Backend query/read adapter를 별도로 두되 같은 `activeProject`에서 단방향 immutable projection을 계산하도록 했다.

물리 파일도 즉시 전면 분할하지 않았다. Source Script 정책상 logical Module decomposition과 physical file hierarchy는 다르며, 이번 단계의 핵심은 logical responsibility와 cross-layer contract다. 물리 분할이 실제 구현에서 필요하면 r24 hierarchy를 보존하는 저수준 파일 배치로 수행할 수 있다.

## 고려했지만 선택하지 않은 방향

- Frontend FSM/renderer의 read-only `activeProject` direct access 유지: plan-016의 read/write 모두 API/Adapter 경계를 통과한다는 요구를 위반하므로 기각했다.
- UI-FSM 전이가 없는 event handler의 Project EFSM direct call 허용: Frontend FSM bypass와 Backend API bypass는 다른 문제이므로 기각했다.
- 모든 read를 Project EFSM command로 처리: 계산/read와 mutation 의미를 불필요하게 결합하므로 기각했다.
- Frontend project mirror/store 추가: `activeProject`와 동기화해야 하는 두 번째 persistent/read authority가 생기므로 기각했다.
- Application boundary를 새 authoritative FSM으로 구성: Project/Frontend state와 중복되는 세 번째 state authority가 되므로 기각했다.
- SELECT_SLOT의 `pendingContentType` 동작 삭제: 기존 observable semantics를 바꾸므로 기각했다. 대신 Application operation에서 selection 뒤 explicit Project command로 분리했다.
- `assets_files.py`, `graphs.py`, `layout_annotations_export.py`, `api_ui.py` 즉시 물리 분할: 논리 hierarchy를 닫는 데 필요하지 않은 파일 이동과 추가 lineage 변경이므로 기각했다.

## 닫힘 판정 영향

r23은 새 Backend/Application/Frontend hierarchy를 포함하지 않으므로 더 이상 최신 Source Script가 아니다.

r24 closure review에서 다음을 확인했다.

- Backend authoritative mutation path가 Project EFSM으로 유지됨.
- Frontend FSM이 Backend를 직접 읽거나 변경하지 않음.
- renderer가 Backend state를 직접 읽거나 mutation하지 않음.
- query와 mutation 경계가 분리됨.
- commit success/failure와 reconciliation ordering이 정의됨.
- SELECT_SLOT conditional mutation 의미가 보존됨.
- lifecycle task owner가 Application boundary로 명확함.
- mixed physical file의 logical owner가 추적 가능함.
- 새 중복 authority나 bus/store를 만들지 않음.

따라서 r24를 closed로 판정했다.

## GitHub 쓰기 경로 진단과 기록 방식

직전 실행에서 실패했던 저수준 Git Data API 경로를 branch를 변경하지 않는 진단으로 다시 확인했다.

- `create_blob`: 성공.
- `create_tree`: 성공.
- parent를 현재 main으로 둔 orphan `create_commit`: 성공.
- main을 현재와 같은 HEAD로 갱신하는 no-op `update_ref`: 성공.

따라서 이전 실패는 Git Data API 자체의 지속적인 권한 차단으로 재현되지 않았고, 당시 호출 상태/형태 또는 일시적 안전성 판정으로만 좁힐 수 있다. 진단 orphan commit은 main에 연결하지 않았다.

사용자 지시에 따라 실제 r24 반영은 이전에 성공했던 GitHub Contents API의 `fetch_file → update_file/create_file` 파일 단위 경로를 사용했다. 이 connector 경로는 한 호출당 한 파일 commit을 생성하므로 r24 Source Script, closure review, lineage, patch pair가 물리적으로 하나의 Git commit에 묶이지 않는 제약이 있다. 대신 각 write 직전에 main HEAD와 대상 blob/path를 재확인했고, 이 `.patch`는 r23 기준 HEAD `b4b4d6c848280cda9fb48f972c59e2eca2c00ba4`부터 r24 lineage 반영 HEAD `5f3c7cf9c8e904b56cbbb31a171f87efefbd7712`까지의 실제 누적 diff를 하나의 coherent 변경 기록으로 고정한다.

이 제약은 변경 의미나 rollback 범위를 숨기지 않기 위해 명시적으로 기록한다.
