# 20260906-001 — inline JavaScript source split

Migration: split-inline-js

## 목적

현재 `Fast-figure.html` 안에 Fast Figure application JavaScript와 vendored Plotly, React/Mantine runtime이 모두 inline으로 들어 있어 코드 검색, 좁은 source fetch, diff context 작성 과정에서 대형 bundle이 작업 대상과 섞이는 문제를 해결한다.

개발 source를 물리적으로 분리하되 application 구조, EFSM, 파일 포맷, DOM 초기화 순서와 portable 동작 의미는 변경하지 않는다.

## 변경 내용

현재 HTML의 inline script body를 GitHub Actions checkout 안에서 직접 추출해 다음 파일로 이동한다.

- `fast-figure.js`: Fast Figure application classic script
- `vendor/plotly.min.js`: 기존 inline Plotly runtime
- `vendor/fast-figure-ui-runtime.js`: 기존 `ff-mantine-runtime` React/Mantine runtime

`Fast-figure.html`에서는 각 원래 script 위치를 동일 순서의 외부 classic script tag로 교체한다.

- `async`, `defer`, `type=module`을 추가하지 않는다.
- `Plotly.setPlotConfig(...)` inline bootstrap은 기존 위치에 유지한다.
- application script도 기존 문서 하단 실행 위치를 유지한다.
- `PACKAGE_FORMAT_VERSION`은 변경하지 않는다.
- 앱 버전만 `1.1.109-alpha`에서 `1.1.110-alpha`로 올린다.

## 추출 방식

대형 vendor bundle을 사람이 다시 복사하거나 모델이 읽어 재작성하지 않는다. Actions가 checkout된 현재 `Fast-figure.html`에서 다음 기준으로 script를 식별한다.

- application: `PACKAGE_FORMAT_VERSION`과 `APP_BUILD` 정의를 포함하는 유일한 inline script
- Mantine runtime: `id="ff-mantine-runtime"`인 유일한 inline script
- Plotly runtime: 위 두 script가 아니며 1 MB를 초과하고 `Plotly`를 포함하는 유일한 inline script

추출한 body의 UTF-8 byte sequence를 그대로 파일에 기록한 뒤 원본 payload와 완전 동일한지 비교한다. 각 파일의 크기와 SHA-256도 Actions log에 남긴다.

## 이 방향을 선택한 이유

현재 문제는 논리적 모듈 구조가 아니라 하나의 거대한 HTML에 application code와 수 MB vendor bundle이 함께 저장된 물리적 구조다. 따라서 ES module화나 함수 재배치를 하지 않고 classic script를 그대로 외부화하는 것이 같은 기능 자유도를 가장 낮은 회귀 위험으로 유지한다.

특히 Plotly/Mantine bundle을 직접 읽고 patch로 재작성하지 않고 checkout 안에서 기계적으로 이동하면 minified vendor source가 모델 context에 들어오지 않고 byte 손상 가능성도 줄어든다.

## 고려했지만 선택하지 않은 방향

### application JS만 분리

향후 application patch는 쉬워지지만 HTML 자체는 여전히 거대한 Plotly/Mantine bundle을 포함해 source fetch와 HTML UI 작업이 계속 불안정하다. 이번 문제를 완전히 해결하지 못하므로 선택하지 않았다.

### ES module 단위 분해

현재 전역 변수/함수 호출 관계와 초기화 순서를 함께 재설계해야 한다. 이번 목적과 무관한 구조 변경과 회귀 위험이 커서 선택하지 않았다.

### `defer` 또는 module script

실행 timing을 바꾸므로 선택하지 않는다. 기존 inline script 위치의 parser-blocking classic script 의미를 그대로 유지한다.

### vendor bundle을 새 버전으로 재빌드

이번 작업은 이동만을 목표로 하므로 dependency/runtime 내용 변경을 하지 않는다.

## 검증

Actions에서 다음을 모두 검사한다.

1. 세 inline script가 각각 정확히 하나만 식별되는지
2. 추출 전 body와 외부 파일 byte sequence가 완전히 동일한지
3. 외부 script tag가 각각 하나만 생성되는지
4. Plotly → Mantine runtime → application의 기존 상대 순서가 유지되는지
5. `Plotly.setPlotConfig` bootstrap이 HTML에 남는지
6. application body가 HTML에 더 이상 inline으로 남지 않는지
7. application JS에 `document.currentScript`, `import.meta` 같은 외부화 민감 의존성이 없는지
8. `node --check fast-figure.js`
9. `node --check vendor/plotly.min.js`
10. `node --check vendor/fast-figure-ui-runtime.js`
11. `git diff --check`

migration 완료 후 실제 전체 변경 diff는 같은 이름의 `.patch`에 binary patch 형식으로 다시 기록한다. 이렇게 하면 minified vendor 코드의 식별자/본문이 검색 결과를 오염시키지 않으면서 `git apply` 가능한 rollback 기록을 유지한다.

## workflow 변경

이 migration 직전에 `.github/workflows/apply-fast-figure-patch.yml`을 source-split 구조에 맞게 갱신했다.

- 허용 patch target을 `Fast-figure.html`, `fast-figure.js`, `vendor/plotly.min.js`, `vendor/fast-figure-ui-runtime.js`로 제한
- split 전에는 기존 inline application syntax 검사 fallback 유지
- split 후에는 외부 JS를 직접 syntax 검사
- 이 문서의 `Migration: split-inline-js` marker에서만 일회성 기계 추출 실행
- migration 결과를 binary patch로 다시 기록

이는 repository patch runner 자체의 인프라 변경이며 application/domain/file semantics를 변경하지 않는다.

## rollback

최종 `20260906-001.patch`를 역적용하면 외부 JS 세 파일이 제거되고 script body가 기존 `Fast-figure.html` 위치로 돌아가도록 기록한다.
