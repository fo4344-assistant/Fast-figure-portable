# 20261002-002 — Source Script file-boundary modular TLC comparison

## 목적

현재 slot-core verification은 \`project_state.py\`,
\`application_fsm.py\`, \`layout_annotations_export.py\`에서 온 상태와
알고리즘을 하나의 PlusCal/TLC 상태공간에서 함께 탐색한다.

사용자 지시에 따라 Source Script의 기존 파일/참조 구조를 1차 검증 경계로 사용하고,
각 파일이 실제로 관찰하는 입력 projection만 경계에 남겨 모듈 단위 TLC 검사를 수행했다.

이번 변경은 canonical verification 의미를 교체하는 것이 아니라
분해 방식의 실행비용을 동일한 2x2 기준선과 비교하는 실험이다.

## 파일 경계

### project_state.py

현재 canonical slot-core slice에서 사용되는 default/local-state/reference/ownership 규칙은
두 stateful unit의 입력 계약으로 projection한다.

이 slice에서 해당 함수들은 순수 predicate/operator이므로
별도의 state walk를 만들지 않는다.

### application_fsm.py

독립 상태로 유지:

- complete slot-local payload
- chart ownership projection
- reset/swap candidate
- command result

외부 입력으로 축소:

- reset target id resolve 성공/실패
- swap source/target visibility
- delegated grid command 성공/실패

grid geometry나 merge state는 이 unit에 복제하지 않는다.

### layout_annotations_export.py

독립 상태로 유지:

- grid rows/cols
- slot row/col/span/hidden
- merge/split/grid state

slot-local payload는 구체 chart/image/caption 조합 대신
\`default/payload-a/payload-b\`로 projection한다.
두 non-default token을 둬 payload identity 보존도 검사한다.

## 비교의 의미

두 방식은 같은 global state graph를 다른 옵션으로 실행한 것이 아니다.

모듈 방식은 의도적으로 다른 파일이 소유한 내부 상태를 제거하고,
현재 파일의 next-state 결정에 필요한 입력 범위만 경계 값으로 둔다.

따라서 비교 대상은:

- global state product를 직접 탐색하는 비용
- interface-complete local state graph들의 합을 탐색하는 비용

이다.

분해 후에도 각 unit 내부에서는 exhaustive TLC를 수행한다.

## 테스트 중 수정

첫 test commit은 workflow의 GitHub expression을 escape한 결과
파일 경로 앞에 역슬래시가 들어가 실행 전 실패했다.
workflow expression 생성만 수정했다.

그 다음 application unit은 PlusCal procedure parameter와 harness \`with\`
변수 이름이 번역 후 중복 선언되어 SANY semantic error가 발생했다.
harness 쪽을 \`chosen*\` 이름으로 분리했다.

첫 성공 후 reset의 current-project id resolve 실패 분기가
고정 SlotIds 때문에 실제로 탐색되지 않는 것을 다시 확인했다.
전체 layout/domain 상태를 되돌려 넣는 대신 \`idsResolved\` boolean input projection을 추가해
원래 branch를 보존했고, 최종 run에서 다시 exhaustive success를 확인했다.

이 세 항목은 verification counterexample이 아니라
실험용 execution model/workflow 구성 문제였으며 최종 파일에는 수정 상태만 남긴다.

## 선택 이유

Source Script는 이미 파일 책임과 참조 관계를 명시한다.
따라서 arbitrary graph partition을 새로 발명하기 전에 이 구조를 1차 경계로 사용하는 것이
의미 추적성과 구현 복잡도 모두에서 가장 작다.

공유 authoritative state가 있다는 이유만으로 producer 내부 상태 전체를 소비자 model에 복제하지 않고,
소비자가 실제 사용하는 input range를 경계 projection으로 두었다.

이 방식이 이번 slice에서 global Cartesian-product 상태 수를 크게 줄이는지
실제 TLC 수치로 확인할 수 있었다.

## 고려했지만 선택하지 않은 방향

### canonical verification model을 바로 모듈형으로 교체

선택하지 않았다.
이번 작업의 목적은 우선 비용 차이와 경계 타당성을 실제 실행으로 비교하는 것이며,
canonical model 교체는 verification-model revision/fingerprint와 validation gate를 바꾸는 별도 결정이다.

### Source Script 파일마다 무조건 하나의 TLC state walk 생성

선택하지 않았다.
\`project_state.py\`에서 현재 slice가 사용하는 항목은 pure contract/operator이므로
인위적인 transition system을 추가하면 Source Script에 없는 동역학을 발명하게 된다.

### 공유 activeProject 전체를 각 unit에 유지

선택하지 않았다.
파일만 나누고 global state product를 그대로 복제하면 이번 분해 목적을 달성하지 못한다.

### 완전 자동 dependency partitioner

선택하지 않았다.
현재 Source Script가 이미 파일/참조 경계를 제공하므로 먼저 명시적 경계의 효과를 검증하는 것이
복잡도가 작고 rollback도 쉽다.
