# 20260831-018

## 목적

Mantine 전환의 기존 `plan-002.md`에서 드러난 방향 오류를 기록하고, 전체 일반 UI를 하나의 React/Mantine shell로 전환하면서 기존 기능/domain EFSM과 UI 상태 region의 의미를 보존하는 새 기준 계획 `plan-003.md`를 추가한다.

## 변경 내용

- `agent_space/plans/plan-003.md`를 추가했다.
- 기존 계획의 문제를 원인별로 기록했다.
  - 점진적 UI 활성 전환으로 legacy/Mantine UI가 장기간 혼재할 위험
  - migration portal이 아키텍처처럼 확대된 문제
  - 실제 사용자 동작을 확인하기 전 비모달 popup 유지 가정
  - Mantine 위에 자체 UI primitive를 다시 만들 위험
  - `@mantine/modals` 사용 여부의 모호한 표현
  - 이미 분리된 EFSM 구조를 다시 분리해야 하는 것처럼 표현한 문제
  - sidebar를 후순위로 두어 전체 UI 전환 목표를 약화한 문제
  - 완료 조건이 legacy UI 잔존을 충분히 막지 못한 문제
- 최종 UI ownership을 하나의 `FastFigureShell`로 정의했다.
- toolbar, sidebar, overlay, menu, 일반 form control을 Mantine 소유로 확정했다.
- Plotly, slot/image surface, layout/label preview 같은 도메인 렌더링 surface만 별도 renderer로 남길 수 있도록 경계를 정의했다.
- 기존 `ApplicationStateMachine`의 기능/domain region과 UI 상태 region의 의미는 유지하고, legacy DOM renderer side effect만 React binding으로 교체하도록 했다.
- 활성 UI cutover는 shell 단위로 한 번에 수행하고, 준비 코드는 이전 커밋에서 작성할 수 있도록 커밋 전략을 정의했다.
- 정적 검색, EFSM, modal, toolbar, sidebar, layout, label, caption, export, asset tree, portable 실행을 포함한 완료/회귀 기준을 구체화했다.

## 이 방향을 선택한 이유

Mantine 도입의 가장 중요한 목적은 일반 UI 규칙을 직접 반복 구현하는 구조를 없애는 것이다. toolbar만 먼저 Mantine로 바꾸고 sidebar나 popup을 legacy로 남기는 방식은 동일 UI 상태를 두 renderer가 나누어 소유하게 만들며 CSS, event binding, 테스트 조합을 늘린다.

반대로 기능/domain EFSM은 현재 이미 UI 상태 region과 분리되어 있으므로 이를 다시 설계하는 것은 불필요하고 위험하다. 따라서 상태기계의 의미와 mutation 경로는 유지하면서 renderer 경계만 교체하는 것이 가장 작은 구조 변경으로 전체 UI 공통화 목적을 달성한다.

## 고려했지만 선택하지 않은 방향

### 기존 `plan-002.md`를 덮어쓰기

선택하지 않았다. 이전 계획에서 왜 방향이 틀어졌는지 추적할 수 있도록 기존 계획을 보존하고 새 계획을 후속 기준으로 두는 편이 개발 이력과 의사결정 검토에 유리하다.

### toolbar부터 Mantine로 활성 전환

선택하지 않았다. UI 혼합 기간이 길어지고 Mantine 도입 목적과 충돌한다.

### 여러 React root / migration Portal

선택하지 않았다. 최종 shell ownership이 불명확해진다. Portal은 Modal/Menu 등 본래 UI 기능에만 사용한다.

### EFSM 재설계

선택하지 않았다. 현재 필요한 것은 renderer side effect 제거이며 기능/domain EFSM과 UI 상태 region의 논리 분리는 이미 존재한다.

### Plotly/dashboard를 React component로 전면 재작성

선택하지 않았다. Mantine가 대체해야 할 일반 UI primitive가 아니며 기능 회귀 위험과 변경 범위만 커진다.

## 검증 및 후속 작업

이 패치는 계획 문서만 변경하므로 application runtime 동작은 변경하지 않는다.

다음 구현 단계에서는 `plan-003.md`의 Commit A에 따라 현재 DOM/FSM 결합 지점을 inventory로 작성하고 각 참조를 domain renderer, legacy UI adapter, 제거 대상 UI infrastructure로 분류한다.

## 패치에 포함되지 않은 사항

- `Fast-figure.html` 코드 변경 없음
- EFSM event/action 변경 없음
- Mantine UI cutover 없음
