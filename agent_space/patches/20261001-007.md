# 20261001-007 — 개발 계층 버전 우선순위 도입

## 목적과 변경 내용

Source Script → pseudocode → source code 순서의 버전 우선순위를 저장소 규칙과 자동 검사로 고정한다.

추가:

- `development-versions.json`
- `scripts/check-development-layer-versions.py`
- `.github/workflows/development-layer-version.yml`

수정:

- `agent_space/AGENT.md`

현재 계층 상태:

- Source Script: revision 1, current
- pseudocode: revision 0, missing
- source code: revision 0, stale / pre-version-chain

현재 source code는 실제로 동작하지만 새 version chain이 생기기 전에 작성된 구현이므로 최신 Source Script/pseudocode에서 내려온 구현이라고 주장하지 않는다.

## 버전 구조

`development-versions.json`이 revision, fingerprint, derived-from 관계의 단일 metadata 원천이다.

실제 의미 우선순위는 다음으로 고정한다.

```text
Source Script
    ↓
pseudocode
    ↓
source code
```

각 layer fingerprint는 파일 내용을 Git blob 방식으로 hash한 뒤 path와 함께 정렬하여 SHA-256으로 다시 묶는다.

따라서 파일 내용이 바뀌면 manifest의 fingerprint도 반드시 달라진다.

## 자동 검사 규칙

- Source Script는 항상 current여야 한다.
- pseudocode가 current이면 현재 Source Script fingerprint를 정확히 참조해야 한다.
- source code가 current이면 현재 Source Script와 current pseudocode fingerprint를 모두 정확히 참조해야 한다.
- source code는 pseudocode가 missing/stale인 동안 수정할 수 없다.
- Source Script/pseudocode/source code의 실제 파일이 변경되면 해당 layer revision을 증가시켜야 한다.
- pseudocode를 수정한 commit은 최종적으로 current 상태여야 한다.
- source code를 수정한 commit은 최종적으로 current 상태여야 한다.
- 실행 가능 여부와 version-chain 최신성은 별개의 상태로 취급한다.

CI는 main push에서 관련 경로가 바뀌면 이 검사를 실행한다.

## 선택 이유

단순한 `v1`, `v2` 숫자만 두면 revision을 올리면서 실제 내용 연결을 잘못 기록할 수 있다.

반대로 fingerprint만 두면 변경 순서를 사람이 추적하기 어렵다.

따라서:

- revision: 계층 안의 시간적 변경 순서
- fingerprint: 실제 내용 동일성
- derived_from: 상위 계층 lineage

세 값을 분리해 사용한다.

## 고려했지만 선택하지 않은 방향

### Source Script 파일마다 독립 version 부여

부분 변경 추적은 세밀하지만 pseudocode/source code가 여러 Source Script module을 함께 참조하므로 lineage가 복잡해진다. 현재 규모에서는 전체 Source Script layer를 하나의 version으로 보는 편이 최소 복잡도다.

### APP_BUILD 문자열에 Source Script version 포함

선택하지 않았다. application release/build version과 개발 계층 lineage는 역할이 다르다.

### Git commit SHA만 사용

commit은 Source Script 외의 문서, 테스트, workflow 변경에도 달라진다. 계층 자체 내용의 동일성을 표시하기에는 layer fingerprint가 더 직접적이다.

### pseudocode가 없는 현재 source code를 current로 표시

선택하지 않았다. 그러면 새로 도입한 우선순위를 시작부터 위반한다. 현재 구현은 runtime baseline으로 존재하지만 version-chain 관점에서는 stale로 명시한다.

## 후속 작업

review-013의 closure blocker를 Source Script에서 해결할 때 source-script revision을 증가시키고 새 fingerprint를 기록한다.

Source Script가 닫힌 뒤 pseudocode를 작성하면 pseudocode revision 1과 현재 Source Script fingerprint를 기록한다.

그 pseudocode 검증 뒤 source code를 수정할 때에만 source-code revision을 증가시키고 두 상위 fingerprint를 기록해 current로 전환한다.
