# 20261001-001 — 브라우저 회귀 검사 범위 정리

## 목적과 변경 내용

브라우저 회귀 검사를 사용자 기능과 파일 의미를 실제로 검증하는 항목으로 축소한다.

제거하는 검사는 다음 다섯 범주다.

- 실제 pre-Mantine FFPX fixture가 없어 항상 blocked로 끝나는 placeholder 검사
- 같은 `File` 객체를 API에 두 번 전달할 뿐 실제 file input의 동일 파일 재선택을 검증하지 못하는 검사
- duplicate DOM/domain ID 검사
- React root/Modal 개수를 이용한 UI ownership 검사
- `dialog` 존재와 특정 함수의 `toString()`을 이용한 legacy dependency 검사

남은 기능 검사는 12개로 다시 번호를 매긴다.

휴지통 이동 cascade 검사는 유지한다. 이 기능은 자산 이동 시 참조 그래프/슬롯 정리가 실제 기능 의미이므로 불필요한 검사가 아니다. 대신 move plan을 검사하기 전에 테스트가 만든 CSV가 실제 선택 chart에 참조되었는지를 먼저 확인해, setup 실패와 `planMove()`의 참조 계산 실패를 구분한다.

`plan-006.md`의 필수 회귀 검사 목록도 같은 기준으로 갱신한다.

## 선택 이유

회귀 검사는 구현 구조 자체를 고정하는 수단이 아니라 사용자 기능과 영속 파일 의미가 깨지는 것을 찾는 수단으로 둔다.

기존 15번의 `.mantine-Modal-root <= 1` 조건은 하나의 React root 안에 여러 Mantine Modal이 존재하는 정상 구조를 실패로 판정했다. 기존 16번은 특정 함수 문자열과 `dialog` 한 종류만 검사하므로 legacy dependency 부재를 증명하지 못한다. duplicate ID와 UI ownership 역시 정적 감사 또는 애플리케이션의 runtime audit가 더 적합하다.

항상 blocked인 검사는 CI 신호를 만들지 못하며, 동일 File API 재호출은 원래 의도인 browser file-input 재선택을 검증하지 못한다.

## 고려했지만 선택하지 않은 방향

### 17개 항목을 유지하고 실패 조건만 완화

선택하지 않았다. 검증 대상 자체가 다른 구조 감사 항목과 잘못 구현된 interaction 검사를 기능 회귀에 계속 남긴다.

### React root 검사만 남기기

선택하지 않았다. single-shell ownership은 현재 구조 설계/정적 감사 대상이며 기능 roundtrip과 같은 CI 실패 조건으로 둘 필요가 없다.

### pre-Mantine FFPX placeholder를 blocked 상태로 유지

선택하지 않았다. 실제 fixture가 생기기 전에는 어떤 호환성도 검증하지 않는다. fixture 확보 시 별도 compatibility fixture 검사로 추가하는 편이 명확하다.

### move-to-trash 검사 제거

선택하지 않았다. 휴지통 진입 시 참조 제거는 실제 프로젝트 기능이며 asset delete와 경로가 다르다. 이 검사는 유지하고 setup 전제만 명확히 한다.

## 검증과 후속 작업

- `browser-regression.js` 구문 검사
- 남은 run 번호가 1~12로 연속인지 확인
- 제거한 helper가 남아 있지 않은지 확인
- split/portable browser regression workflow 재실행
- portable runner가 여전히 완료 신호를 받지 못하면 테스트 항목 수와 별개 문제로 분리해 조사

애플리케이션 소스, EFSM, project model, 파일 schema는 변경하지 않는다.
