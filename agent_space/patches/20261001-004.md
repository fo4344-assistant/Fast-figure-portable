# 20261001-004 — Source Script 역작성 1차

## 목적과 변경 내용

현재 Fast Figure source code를 개발 정책의 Source Script 단계로 되돌려 검토하기 위해 `sourcescript/`를 추가한다.

추가 파일:

- `sourcescript/system.py`
- `sourcescript/project_state.py`
- `sourcescript/application_fsm.py`
- `sourcescript/assets_files.py`
- `sourcescript/graphs.py`
- `sourcescript/layout_annotations_export.py`
- `sourcescript/api_ui.py`
- `sourcescript/renderer_runtime.py`
- `sourcescript/portable_build.py`

Source Script는 Python을 최종 구현 언어로 정하지 않는다. Python 문법은 데이터 형태, 공통 식별자, 함수 경계, 상태 변경, 처리 순서와 미확정 사항을 기록하는 authoring notation으로만 사용한다.

이번 변경은 source code를 수정하지 않는다.

## 역작성 기준

현재 `main`의 다음 구현을 원천으로 사용했다.

- `fast-figure.js`: ProjectObject, ApplicationStateMachine, FastFigureApi, project VFS, graph/annotation/layout/export renderer, FFPX/FFSX.
- `fast-figure-ui.js`: React/Mantine frontend, UI-local draft/Modal/pointer state.
- `Fast-figure.html`: renderer host와 script/CSS load boundary.
- `scripts/build-portable.py`: split source를 single-file portable HTML로 결합하는 규칙.
- vendor runtime/Plotly: 외부 renderer/runtime 원천.

공통 식별자는 가능한 한 현재 구현 이름을 유지했다. 구현에 없는 새 domain state, 새 router, 새 schema를 Source Script에서 발명하지 않았다.

## 현재 코드에서 Source Script로 올린 미확정 사항

### label preview position

현재 `previewLabelsApiPosition`은 이름상 preview지만 `activeProject.labelSettings.x/y`를 즉시 변경하고, `commitLabelsApiPosition`은 최종 notify만 수행한다.

따라서 다음 단계에서 둘 중 어느 의미가 원래 의도인지 정해야 한다.

- drag 중 변경 자체가 authoritative continuous edit다.
- drag 중 값은 preview draft이고 commit에서 authoritative state가 바뀌어야 한다.

이번 역작성에서는 어느 쪽도 새 정책으로 결정하지 않고 `system.py`와 `layout_annotations_export.py`에 미확정으로 표시했다.

### telemetry projection

현재 `debugEnabled`와 `uiTelemetryState.debugEnabled`가 함께 존재한다. 첫 작성본에서는 전자를 runtime authority, 후자를 UI read projection으로 기록했다. projection이 이후 mutation의 독립 원천으로 확대되지 않는지는 pseudocode 번역 전에 다시 확인한다.

### runtime references

`selectedSlotId`, `editing`은 persistent ProjectObject에 포함되지 않는다. 첫 작성본에서는 각각 UI/runtime selection과 core-internal chart pointer로 기록했다. 특히 `editing`이 반드시 유지해야 할 runtime state인지 단순 파생 가능한 cache인지는 다음 구조 검토 대상으로 남겼다.

## 선택 이유

한 파일에 전체 구현을 복사하면 함수 목록은 만들 수 있지만 책임 경계와 참조 원천을 다시 검토하기 어렵다. 현재 구현의 실제 책임 단위에 맞춰 project state, FSM, assets/files, graph, layout/annotation/export, API/UI, renderer runtime, portable build로 분리했다.

다른 Source Script의 책임을 다시 반복하지 않고 파일 상단의 참조 관계로 연결했다.

## 고려했지만 선택하지 않은 방향

### 현재 JavaScript를 Python 문법으로 기계 번역

선택하지 않았다. 저수준 DOM/라이브러리 구현까지 고정하고 Source Script가 pseudocode 이전의 구현 명세가 아니라 두 번째 source code가 된다.

### Source Script 한 파일만 작성

선택하지 않았다. project state, FSM, file format, renderer, frontend 책임이 한 파일 안에서 반복되며 다음 pseudocode 단계에서 참조 원천과 변경 경계를 추적하기 어렵다.

### 발견한 구조 문제를 즉시 source code에서 수정

선택하지 않았다. 이번 단계는 source code -> Source Script 역검토다. 상위 의미가 미확정인 상태에서 구현을 먼저 바꾸면 Source Script가 구현을 사후 정당화하게 된다.

### pseudocode도 동시에 작성

선택하지 않았다. 개발 정책상 Source Script가 구조적으로 닫힌 뒤 별도의 언어 중립 pseudocode 단계에서 실행 순서와 실패 경로를 검증해야 한다.

## 검증 및 후속 작업

- 새 Source Script가 현재 구현의 실제 identifier/reference를 추적할 수 있는지 검사한다.
- Source Script 안에서 project authority와 runtime projection을 구분한다.
- 미확정 항목을 임의로 결정하지 않는다.
- 다음 단계에서는 Source Script를 먼저 검토·수정한 뒤 pseudocode를 별도 작성한다.
- source code 수정은 pseudocode 검증 뒤의 다음 구현 단계에서만 진행한다.
