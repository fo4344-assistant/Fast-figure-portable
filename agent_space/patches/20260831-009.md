# 20260831-009

## 목적

React/Mantine runtime을 외부 네트워크 의존성 없이 `Fast-figure.html`에 vendoring하기 위한 일회성 GitHub Actions builder를 추가한다.

## 변경 내용

- `.github/workflows/vendor-mantine-runtime.yml`을 추가한다.
- workflow는 자신의 추가 커밋이 main에 push될 때만 경로 조건에 의해 후보가 된다.
- job 수준에서 actor와 정확한 커밋 메시지를 다시 검사해 한 번만 실행되도록 제한한다.
- React/ReactDOM 19.2.8, `@mantine/core`/`@mantine/hooks` 9.5.2, esbuild 0.25.9를 임시 runner 작업공간에만 설치한다.
- 결과 runtime/CSS를 `Fast-figure.html`에 삽입하고 README/Licence 고지를 함께 갱신한다.
- 생성 결과 커밋에는 `20260831-010.patch`와 동명 설명 파일을 자동으로 포함한다.
- 결과 커밋은 workflow 파일을 변경하지 않으므로 workflow를 재실행하지 않는다.

## 이 방향을 선택한 이유

현재 작업 환경에서는 npm registry 직접 접근이 안정적이지 않지만 GitHub Actions runner에서는 npm 기반 재현 가능한 bundle 생성이 가능하다. runtime bundle 자체를 수동 복사하지 않고 exact package version과 esbuild 명령으로 재현 가능하게 만드는 편이 안전하다.

workflow를 상시 build system으로 확대하지 않고 특정 커밋에서 한 번만 실행되도록 하여 단일 HTML canonical source 원칙과 불필요한 자동화 반복을 모두 유지한다.

## 고려했지만 선택하지 않은 방향

- CDN에서 React/Mantine를 runtime load하는 방식은 offline portable 요구와 충돌해 선택하지 않았다.
- package manager/build system을 프로젝트 상시 구조로 추가하는 방식은 현재 single-file 프로젝트에 불필요한 복잡도를 추가하므로 선택하지 않았다.
- workflow를 patch 파일 변경마다 반복 실행하는 방식은 무한 실행 및 불필요한 build 위험이 있어 선택하지 않았다.

## 안전장치

- trigger path는 workflow 파일 하나로 제한한다.
- GitHub Actions bot이 만든 커밋에서는 job이 실행되지 않는다.
- 정확한 setup commit message에서만 job이 실행된다.
- concurrency group 하나를 사용하고 자동 재시도 loop를 만들지 않는다.
- 결과 commit은 workflow trigger path를 변경하지 않는다.

## 패치에 포함되지 않은 변경사항

실제 React/Mantine runtime 삽입은 workflow가 만드는 다음 커밋 `20260831-010`에서 기록된다. 이 patch와 설명 파일 자체는 재귀적으로 diff에 포함하지 않는다.
