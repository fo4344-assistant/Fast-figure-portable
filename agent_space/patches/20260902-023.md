# 20260902-023 — graph object 선택 command / legacy renderer 분리

## 목적

Mantine graph object 목록에서 항목 선택을 수행할 때 기존 `selectGraphObject()`를 그대로 호출하면 legacy form DOM과 preview renderer까지 함께 갱신된다.

기존 함수에는 다음 두 책임이 섞여 있다.

1. 기능 상태
   - `SELECT_GRAPH_OBJECT` / `CLEAR_GRAPH_OBJECT`
   - 선택된 object의 CSV를 `activeCsvId`, `activeDataName`에 반영
2. legacy renderer
   - `headerLines.value`
   - `loadData()`를 통한 전역 `rows/columns`, native X/Y select, preview/status 갱신
   - `populateObjectForm()`
   - `updateTypeSpecificOptions()`
   - `renderGraphObjects()`

이번 패치는 이 두 책임을 분리해 Mantine list가 DOM-free selection command를 사용할 수 있게 한다.

## 변경 내용

- 앱 버전 `1.1.68-alpha` → `1.1.69-alpha`
- `selectGraphObjectFromIndex(index, expectedChartId)` 추가
- UI bridge에 `selectGraphObject(index, chartId)` 추가
- 기존 `selectGraphObject(index)`는 공통 command 호출 뒤 legacy renderer 작업만 수행하도록 변경

공통 command 흐름:

```text
selectGraphObjectFromIndex(index, expectedChartId)
→ selected chart identity 검증
→ SELECT_GRAPH_OBJECT / CLEAR_GRAPH_OBJECT
→ 기존 graphObject EFSM action
→ 선택 object의 csvId가 유효하면 activeCsvId / activeDataName 갱신
```

## 기존 기능 의미 보존

기존 선택 동작은 같은 index를 다시 누르면 선택이 해제되는 toggle이다. 공통 command도 이를 그대로 유지한다.

선택 시 object가 참조하는 CSV를 active CSV로 만드는 동작도 유지한다. 이는 이후 `addGraphObject` 등이 `activeCsvId`를 사용하므로 단순 renderer side effect로 제거하지 않는다.

반대로 다음 항목은 기능 상태의 source of truth가 아니라 legacy UI 갱신이므로 공통 command에 넣지 않는다.

- `#headerLines` 값 쓰기
- `loadData()`
- native X/Y `<select>` option 생성
- `populateObjectForm()`
- legacy graph object list 다시 렌더

활성 legacy `selectGraphObject()` wrapper에서는 위 renderer 동작을 계속 실행하므로 현재 사용자 동작은 변하지 않는다.

## `loadData()` 분류

구형 기준 구현을 좁게 확인한 결과 `loadData()`는:

- 전역 `rows`, `columns` 갱신
- native `xCol`, `yCol` option/value 갱신
- build box 표시
- preview/status 갱신

을 한 함수에서 수행한다.

Mantine object form은 이미 object가 참조하는 project CSV에서 column definition을 직접 계산하므로 selection command에서 `loadData()`를 호출할 이유가 없다.

현재 legacy wrapper에서는 기존 동작 보존을 위해 계속 호출한다.

## stale callback guard

`expectedChartId`가 현재 selected chart와 다르면 command를 수행하지 않고 `false`를 반환한다.

이 값은 source of truth가 아니라 이전 chart의 list callback이 현재 chart selection을 변경하지 못하도록 하는 identity guard다.

## source of truth

- graph object selection: 기존 graphObject EFSM + `selectedObjectIndex`
- graph object data: selected chart `editor.objects`
- active CSV: 기존 `activeCsvId`
- React list snapshot: 비권위 render snapshot

새 selection state를 React에 만들지 않는다.

## 최소복잡도

기존 selection 의미를 Mantine용으로 복제하지 않고 하나의 command로 합친다.

legacy 경로:

```text
legacy click
→ selectGraphObject()
→ selectGraphObjectFromIndex()
→ 기존 EFSM
→ legacy renderer sync
```

Mantine 경로:

```text
Mantine click
→ bridge.selectGraphObject()
→ selectGraphObjectFromIndex()
→ 기존 EFSM
```

## 변경하지 않는 영역

- `applyGraphObjectSelectionAction`
- `GRAPH_OBJECT_EVENTS`
- `saveGraphObjects()`
- reorder/color/delete/add 동작
- graph object schema
- trace 생성
- Plotly renderer 및 인라인 Plotly library
- import/export

## 선택하지 않은 방향

### Mantine에서 기존 `selectGraphObject()` 직접 호출

선택하지 않는다. legacy native form/preview renderer를 계속 요구하게 되어 UI ownership 분리가 되지 않는다.

### selection 시 `activeCsvId` 갱신 제거

선택하지 않는다. 기존 `addGraphObject` 등 기능이 active CSV를 사용하므로 사용자 관찰 가능한 의미를 바꿀 가능성이 있다.

### `loadData()` 자체를 이번 패치에서 분해

선택하지 않는다. CSV preview/native form 전반에 영향을 주는 더 큰 작업이며 selection command 분리에 필요하지 않다.

### 새 EFSM event 생성

선택하지 않는다. 기존 `SELECT_GRAPH_OBJECT` / `CLEAR_GRAPH_OBJECT`가 이미 정확한 상태 의미를 담당한다.

## 회귀 위험

낮음~중간이다. 활성 legacy 함수의 내부 경로가 바뀌지만 event와 renderer 결과는 동일하게 유지한다.

검사 항목:

- 같은 object 재클릭 시 clear
- 다른 object 클릭 시 selected index 이동
- 선택 object의 CSV가 active CSV가 됨
- legacy `headerLines`, X/Y controls, object form 갱신 유지
- stale chart callback 거부
- image/no-chart 상태에서 write 없음
- EFSM event/action diff 없음
- Plotly/trace 영역 diff 없음

## rollback

1. bridge `selectGraphObject` 제거
2. `selectGraphObjectFromIndex()` 제거
3. legacy `selectGraphObject()`에 기존 event + active CSV 코드를 복원
4. 앱 버전을 `1.1.68-alpha`로 복원

`021/022` 목록 read model은 독립 유지 가능하다.

## 후속

적용 후 목록 color/delete/reorder의 command 경계를 별도로 검토한다.

특히 기존 `saveGraphObjects()`는 `selectedGraphObjectGuard()`를 요구하므로, 선택되지 않은 row의 color/delete 동작이 의도된 것인지 먼저 확인하고 Mantine action을 연결한다. 이 부분은 추측으로 guard를 제거하지 않는다.
