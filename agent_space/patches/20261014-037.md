# 20261014-037 — Backend Project EFSM / Frontend FSM API-Adapter 경계 계획 추가

## 목적과 변경 내용

새로운 Backend–Frontend 계층 요구를 실행 가능한 작업 계획으로 기록하기 위해 agent_space/plans/plan-016.md를 추가한다.

plan-016은 기존 plan-015를 덮어쓰지 않는다. plan-015는 Project EFSM과 interface FSM 분리가 완료된 당시의 실행 이력으로 유지하고, 새 계획은 그 이후 확정된 다음 요구 때문에 기존 구조에서 다시 열어야 하는 경계를 명시한다.

- Project EFSM을 Backend 책임으로 취급한다.
- Frontend FSM을 Frontend 책임으로 취급한다.
- Backend와 Frontend 사이의 mutation, query/read, result/reconciliation은 API 또는 Adapter를 통해서만 통신한다.
- Frontend component/FSM/renderer가 activeProject, projectEFSM 및 Backend domain helper를 직접 사용하지 않는다.
- Backend는 Frontend FSM, DOM, Mantine/React state를 직접 변경하지 않는다.
- existing FastFigureApi, application orchestration, ProjectMutationResult를 우선 재사용하고 같은 의미의 새 bus/store/facade를 중복 생성하지 않는다.
- Source Script에서 Backend / Application boundary / Frontend Module decomposition hierarchy를 먼저 확정한 뒤 PlusCal, verification model, Source Code 순서로 전파한다.
- 현재 Fast Figure AGENT.md가 요구하는 verification-model/TLC gate를 그대로 적용하고, TLC pending을 새 Source Code 완료로 간주하지 않는다.

계획에는 현재 Source Script에서 직접 확인된 dependency와 수정 대상, Project EFSM mutation contract, Frontend state ownership, query/read boundary, mutation result와 reconciliation, lifecycle orchestration, renderer input, selection/reference contract, FFPX persistence, DOM/Mantine local state, dependency audit 범위, 파일별 Source Script 변경 계획, PlusCal 번역 계획, verification/TLC 계획, Source Code 구현 계획, 회귀검사, 패치 단위, 중단 조건, 완료 조건 및 최종 허용/금지 경로를 각각 별도 절로 기록했다.

## 해당 방향을 선택한 이유

현재 Source Script는 project_efsm.py와 interface_fsm.py를 이미 분리하고 FastFigureApi와 application_fsm.py의 orchestration도 갖고 있으므로 새 상태기계나 별도 project store를 만드는 것보다 기존 구조의 공식 cross-layer boundary를 강화하는 것이 중복이 가장 적다.

또한 source-script-policy.md의 Module decomposition hierarchy 보존 규칙 때문에 Backend/Frontend 의미 계층을 Source Code에서 먼저 추가할 수 없다. 사용자 요구가 새로운 의미적 책임 배치를 확정하므로 Source Script에서 hierarchy와 API/Adapter contract를 먼저 정의하고 하위 계층에 직접 전파하는 순서를 계획에 명시했다.

## 검토했지만 선택하지 않은 방향

- plan-015 직접 수정: 이미 완료 기록과 당시 판단 근거가 있어 과거 실행 이력을 덮어쓰므로 선택하지 않았다.
- Frontend event handler가 UI-FSM 전이가 없을 때 projectEFSM을 직접 호출하도록 허용: 새 Backend–Frontend API/Adapter 경계를 우회하므로 기각했다.
- read-only access만 activeProject 직접 참조 허용: mutation 경로와 별개로 새 계층 계약이 Backend internal state의 Frontend 직접 접근을 금지하므로 기각했다.
- 새 command bus/event bus/project mirror 도입: FastFigureApi, application orchestration, ProjectMutationResult가 이미 같은 책임의 기반을 제공하므로 불필요한 중복 abstraction이 된다.
- renderer를 Backend 쪽으로 이동: renderer가 Mantine/DOM/Plotly와 Frontend runtime selection을 함께 다루므로 이번 요구에서 Frontend 책임으로 유지하고 Backend data는 read adapter projection으로 공급한다.
- TLC를 이번에도 선택 단계로 취급: 현재 agent_space/AGENT.md가 Fast Figure에서 TLC gate를 명시적으로 요구하므로 정책 변경 없이 완화할 수 없다.

## 관련 전제와 후속 작업

이 패치는 계획 문서만 추가한다. Source Script, PlusCal pseudocode, verification model, application source, development-versions.json은 수정하지 않는다.

실제 구현은 plan-016의 순서에 따라 Source Script architecture patch부터 시작해야 하며, 기존 plan-015 완료 상태를 곧바로 새 구조의 완료로 간주하지 않는다.

현재 development-versions.json의 source-code.status=current와 verification-model.tlc=pending 조합은 AGENT.md의 현 gate 문구와 불일치하므로, plan-016의 새 Source Code revision을 current로 닫기 전에 이 정책 조건을 실제 TLC passed로 만족시키거나 사용자가 별도로 정책을 변경해야 한다.
