# 20260901-017

## 목적

Commit B staging에서 아직 placeholder였던 README overlay의 본문을 실제 README 문서로 교체한다. README outer overlay는 이미 Mantine controlled Modal이므로 새 Modal을 중첩하지 않고 content renderer만 추가한다.

## 변경 내용

- 애플리케이션과 built-in README 버전을 `1.1.47-alpha`로 올린다.
- `fastFigureUiBridge.readReadmeHtml()`을 추가한다.
- 기존 `#readmeDialog .readme-content`를 정적 문서 소스로 복제하되 legacy `#closeReadme` 버튼은 제거한 HTML만 반환한다.
- `FastFigureReadmeContentStaging`을 추가한다.
- 기존 staging README `FastFigureOverlayModalStaging`은 그대로 사용하고 placeholder `Text`만 실제 README content component로 교체한다.
- README 본문은 Mantine `ScrollArea` 안에 읽기 전용으로 렌더링한다.
- staging export 목록에 `FastFigureReadmeContentStaging`을 추가한다.

## 실패 재검토

첫 큐는 README placeholder hunk의 new line count를 잘못 기록해 `corrupt patch`로 중단되었다. 두 번째 큐는 outer README block 전체를 교체하려 한 문맥이 현재 source와 맞지 않아 `git apply --check`에서 중단되었다. 그 결과 outer Modal을 유지하고 content renderer만 교체하는 더 작은 구현으로 수정했다.

세 번째 큐는 수정된 구현의 삽입 hunk에서 문맥 2줄과 추가 본문 15줄을 합친 new count가 17이어야 하는데 잘못 기록되어 `corrupt patch`로 중단되었다. 해당 hunk count를 `2→17`로 정정했다. 앞선 실패 실행들은 모두 HTML 적용 전에 중단되었다.

네 번째·다섯 번째 큐는 패치 자체는 독립 파서에서 정상적으로 읽혔지만 `git apply --check`에서 중단되었다. 이 시점에서 기존 hunk 번호를 누적 line delta로 추정하는 방법을 중단하고, 현재 `main`의 `Fast-figure.html` blob(`651a1b095966c7a1a43a29b2bdd8539a89d85c9b`)을 직접 읽어 각 변경 위치의 실제 문맥과 행 번호를 확인했다.

확인 결과 실패 원인은 다음 두 가지였다.

1. Mantine runtime/CSS vendoring으로 파일 앞부분에 수천 줄이 추가되어 README와 애플리케이션 코드의 실제 위치가 과거 patch의 11k/14k대 hunk 번호에서 크게 이동했다. 대용량 단일 파일에서 `git apply`의 큰 offset 탐색에 계속 의존한 것이 부적절했다.
2. 더 중요한 문맥 오류가 있었다. 과거 source에서는 `useFastFigureFsmSnapshot()` 주변에 overlay host가 가까이 있었지만 현재 main에서는 그 사이에 Toolbar/Sidebar/Layout/Label/Caption/Print staging 구현이 이미 추가되어 있다. 따라서 `}` 바로 다음에 `FastFigureOverlayHostStaging()`이 온다는 017의 삽입 hunk 문맥 자체가 현재 source와 일치하지 않았다.

현재 main 문맥으로 다시 작성한 다음 실행에서는 Actions의 실제 job log를 직접 확인했다. `git apply --check`가 보고한 실패 위치는 `Fast-figure.html:18952` 하나뿐이었다. 이는 앞선 hunk들을 다시 추측해 수정할 근거가 없음을 의미하므로 그대로 유지한다. 실패한 README placeholder hunk는 시작 행 자체는 맞았지만 변경 대상 한 줄만 앞 문맥으로 둔 매우 좁은 hunk였다. 이를 outer `FastFigureOverlayModalStaging` 호출부터 닫는 괄호까지의 실제 current-main 문맥으로 확장하여 위치 판별을 안정화한다.

재작성 패치는 README content component를 현재 `FastFigurePrintModalStaging()`의 끝과 `FastFigureOverlayHostStaging()`의 시작 사이에 배치한다. 이는 기능 의미도 더 직접적이며 기존 staging component 순서를 보존한다.

## 이 방향을 선택한 이유

README는 프로젝트 상태가 아니라 애플리케이션에 포함된 정적 문서이다. 수백 줄의 동일 본문을 React용 상수로 다시 복사하면 문서 원본이 둘이 되고 버전·라이선스·링크 갱신이 어긋날 수 있다. cutover 전에는 기존 본문을 정적 소스로 재사용하고, cutover 시 legacy `<dialog>` 껍데기를 `<template>` 또는 동등한 비활성 문서 소스로 바꿀 수 있다.

재사용되는 것은 문서 본문뿐이며 legacy popup lifecycle과 닫기 버튼은 staging에서 사용하지 않는다.

## 선택하지 않은 방향

- README 본문 전체를 JavaScript 문자열로 중복 복사하지 않는다.
- 새 Mantine Modal을 기존 Mantine README Modal 안에 중첩하지 않는다.
- legacy dialog의 `showModal()`, `close()`, cancel/backdrop handler를 staging에서 호출하지 않는다.
- 전체 shell cutover는 수행하지 않는다.
- 감사에서 지적된 문서 디렉터리 운용, workflow cleanup, 버전 정책은 이번 패치 범위에 포함하지 않는다.

## 검증 항목

- `git apply --check`
- `git diff --check`
- 메인 JavaScript `node --check`
- APP_BUILD와 built-in README 버전 일치
- staging README에서 legacy close control/lifecycle 미사용
- overlay open/close의 EFSM 의미 유지
- README 본문 단일 원본 유지
- patch hunk가 현재 main blob의 실제 문맥을 기준으로 작성되었는지 확인

## 패치에 포함되지 않은 변경사항

이 `.patch`와 설명 `.md` 자체는 재귀적인 diff에 포함하지 않는다. 실제 HTML 수정은 제한된 patch workflow가 검증 후 적용한다.
