## 적용한 변경과 판단

### A. representation별 검증 — 기존 validator 공유

`sourcescript/graphs.py`의 `validateChartModel`이 실제 project CSV object와 non-editable imported conversion view를 구별한다. 후자는 project CSV resolve를 요구하지 않지만 conversion table/column/style, chart/Plotly/imported 구조는 검증한다. `conversionRows`의 존재와 non-editable 상태로 기존 representation을 식별하며 새 면제 registry/validator/가짜 CSV를 추가하지 않는다. 이미 실제 CSV를 가진 일반 chart는 편집을 잠시 꺼도 그 CSV 참조 검증을 유지한다.

`sourcescript/project_state.py`의 whole-project 검증과 `sourcescript/assets_files.py`의 reference 수집, FFPX/FFSX read/write/apply가 같은 판정을 사용한다. conversion view가 package CSV 수집/remap 대상에 끼지 않는다. editable 전환은 command 내부에서 필요한 CSV/id/path와 object 참조를 함께 계산한다. zero-object에는 fake CSV를 만들지 않으며 이미 project CSV로 전환된 chart의 CSV를 다시 생성하지 않는다.

### B. candidate ownership — current authority에서 계산

`sourcescript/application_fsm.py`, `sourcescript/project_efsm.py`의 공통 경로에 따라 wrapper는 identity/new input/file/완료된 choice만 전달한다. `sourcescript/assets_files.py`, `sourcescript/graphs.py`, `sourcescript/layout_annotations_export.py`의 기존 builder는 command 내부 Backend 계산으로 구별한다. wrapper가 whole-project/model/objects candidate를 만들고 command로 다시 넘기는 경로를 제거했다.

- 파일과 순수 parsing 입력을 current VFS/id/path/target에 의존하는 candidate와 구별한다.
- collision prompt는 Application 소유이며 Backend가 callback/UI resolver를 호출하지 않는다.
- 비동기 file 처리 뒤 current authority를 다시 확인한다. replace 대상 identity/path가 달라지면 자동 재선택/덮어쓰기하지 않는다. candidate의 기준 authority가 바뀌면 재계산·검증한다.
- Project 실패/취소/거부는 부분 commit이나 성공 reconciliation/render를 발생시키지 않는다. 기존 lifecycle의 busy/ready/error 알림과 Project commit 성공을 혼동하지 않는다.

### C. selection hint — 기존 성공 reconciliation에서 한 번 소비

기존 `ProjectMutationResult.selectionHints`가 대상 chart와 optional index를 전달하고 `buildFrontendReconciliationInput`이 post-commit chart/index를 검증한다. hint 없음은 이전 index 유지 후보, explicit none은 clear다. Frontend는 검증된 최종 scalar를 소비하며 별도 사후 `SELECT_GRAPH_OBJECT`나 hint 상태 저장소를 추가하지 않는다.

- 이동은 기존 `from/to`의 `to`를, 삭제는 기존 선택 해제를 유지한다. 추가는 command가 계산한 새 object 위치를 쓴다.
- `[A,B,C]`에서 B(index 1)를 0으로 옮기면 유효하지만 다른 object인 옛 index 1을 유지하지 않고 hint 0을 검증한다.
- 다른 chart의 hint는 현재 chart 선택에 적용하지 않는다. non-editable/없는 chart/범위 밖 index는 clear한다.
- 인덱스 보정은 독립 current CSV를 변경하지 않는다. 명시적 object 선택의 CSV 연동과 구별한다.

### D. 공개 반환 정합화 — 완료 주장 아님

수정한 chart add/object-value/editable wrapper와 CSV/image 생성, batch/slot/project import wrapper는 공통 Application 반환 triple을 공개 chart/asset/settings로 위장하지 않는다. 성공 뒤 기존 공식 query의 detached 결과를 취득하고 실패 결과/예외/취소는 성공 read로 바꾸지 않는다. 생성/import의 실제 id/path는 기존 `ProjectMutationResult.changed`에서 얻으며 새 result envelope를 만들지 않는다.

`sourcescript/api_ui.py`는 move/delete의 기존 입력과 hint 의미, project import의 post-commit snapshot 반환을 기존 operation 기술에 맞췄다. `sourcescript/layout_annotations_export.py`는 다른 layout/annotation mutation도 wrapper의 새 입력 전달과 command 내부 candidate 계산을 구별한다. **전체 public API의 호출/반환/실패 trace가 끝났다는 의미는 아니다.**

### E. renderer — resource lifetime 일부 구체화

`sourcescript/renderer_runtime.py`의 기존 `renderDashboard`에 host/slot/chart identity 기준 재사용/교체/purge, 현재 geometry 적용 뒤 resize, 오래된 generation/host 결과 폐기, image surface의 display handle/URL 소유·교체·해제를 기술했다. generation/instance 연결은 renderer-local lifetime 정보이며 Project/Frontend의 두 번째 authority가 아니다. 여러 image surface 중 하나의 정리가 다른 surface의 자원을 무효화하지 않아야 한다.

`sourcescript/project_state.py`의 image query는 copied bytes/순수 display URL projection이며 revocable resource를 할당하지 않는다. resource를 실제 생성하는 renderer가 그 lifetime을 소유한다. 구체 Plotly/DOM API 문법이나 scheduler primitive는 고정하지 않는다.

## 검증 방법과 한계

- 로컬은 파일/Git diff/hash/transport만 사용한다. Source Script/application/checker/test/build/TLC를 로컬 실행하지 않는다. helper/temp는 작업 디렉터리 아래 `.work/`만 사용한다.
- fingerprint는 업로드할 canonical LF Git blob과 정렬 path 레코드로 계산한다. 이 byte 계산은 semantic checker 실행이 아니다.
- `.github/workflows/development-layer-version.yml`에 선택적 manual `base_sha` 입력을 추가해 기존 checker를 작업 기준 commit부터의 누적 diff에도 실행할 수 있게 한다. push 동작은 기존 `github.event.before`를 유지한다. 새 checker/framework는 추가하지 않는다.
- 실제 GitHub Actions run/head/result와 실제 누적 patch endpoint는 `agent_space/patches/20261016-010.md`에 기록한다. metadata checker 성공은 Source Script의 논리 닫힘이나 browser/build/TLC 성공이 아니다.
- Contents API 게시가 여러 commit이므로 중간 source/metadata/patch 상태는 불완전할 수 있다. patch 자체와 그 설명은 semantic endpoint 뒤에 기록하며 자기참조를 제외한다.
